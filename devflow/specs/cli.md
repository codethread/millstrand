# CLI Surface

**Document ID:** `SPEC-002` **Status:** Implemented **Last Updated:** 2026-09-05 **Related RFCs:** [RFC-019 Op-only CLI](../archive/26-07-04__op-only-cli/rfcs/2026-07-04-op-only-cli.md), [RFC-002 Task Query DSL](../rfcs/2026-06-24-task-query-dsl.md), [RFC-003 Fast JSON Socket CLI](../archive/26-06-25__go-cli-migration/rfcs/2026-06-25-fast-json-socket-cli.md), [RFC-004 Go CLI Migration](../archive/26-06-25__go-cli-migration/rfcs/2026-06-25-go-cli-migration.md) **Code:** `cli/`, `src/millstrand/core/weaver`, `src/millstrand/api/weaver/alpha.clj`, `.millstrand/workflows.clj` (this repository's coordination workspace; application workspaces use `.millstrand` or `.ms`)

## SPEC-002.P1 Purpose

The public CLI is two thin Go binaries. `mill` owns routing and supervision, workspace bootstrap, weaver lifecycle, trusted nREPL attach, and client-side execution that must preserve the caller's terminal, cwd, and environment. `strand` is a pure dispatcher for registered weaver ops: it resolves selection context, assembles one invoke envelope per call, and relays NDJSON back. `strand` has **zero builtin subcommands**: every command name is a weaver-registered op (SPEC-004.C63a–c). The Batteries command surface and its listing behavior are specified in [`spools/batteries.md`](../../spools/batteries.md). Other reference spools document their ops in their own spool docs.

## SPEC-002.P2 Interface

Entrypoints:

```text
strand [dispatcher-flags] <op-name> [args...]
strand --help | -h | --version
strand --dry-run [dispatcher-flags] <op-name> [args...]

mill --version
mill changelog
mill start [--json]
mill status [--json]
mill weaver list
mill init [--workspace <dir>] [--auto-start]
mill init --stealth [--auto-start]
mill weaver start [--workspace <dir>] [--name <name>] [--ready-timeout <dur>] [--json]
mill weaver restart [--workspace <dir>] [--ready-timeout <dur>] [--json]
mill weaver status|stop [--workspace <dir>] [--json]
mill weaver repl [--stdin] [--workspace <dir>]
mill prime millstrand
mill bin list
mill bin build <bin>
mill bin run <bin> [args...]
```

Dispatcher flags: `--workspace <dir>`, `--cwd <dir>`, `--worktree-root <dir>`, `--git-common-dir <dir>`, `--stdin`, `--payload name=path` (repeatable), `--timeout <dur>`, `--dry-run`, `--version`, `--help` (`-h` is an equivalent top-level alias).

## SPEC-002.P3 Dispatcher contracts

- **SPEC-002.C1:** Public `strand` commands require a reachable local `mill` entrypoint. If no mill is running or its metadata/socket is stale, commands fail non-zero with remediation to run `mill start`. If a live mill's metadata carries a different product version or mill protocol version than the invoking `strand` binary, commands fail non-zero naming the mismatched identities, both build identities when stamped, and the metadata path, with remediation to align versions (rebuild `strand` to match the running mill, or restart mill from the newer build) — never the `mill start` remedy, which is misleading while a mill runs. A stamped release treats missing product identity as skew, not as legacy-compatible metadata.
- **SPEC-002.C1a:** `--workspace` selects a Millstrand workspace and is the highest-precedence override. Without it, implicit repo selection requires cwd to be inside a supported non-bare Git worktree; the selected workspace is the canonical repository `.millstrand` or `.ms` directory derived from the absolute Git common directory. Linked worktrees for one repository therefore select the same default workspace. The unsupported legacy workspace name is rejected as an application marker. Outside supported Git layouts, no-flag commands fail loudly rather than creating cwd workspaces. Runtime state, sockets, metadata, and SQLite data live under mill-owned XDG state paths, not inside the selected workspace.
- **SPEC-002.C2:** Client JSON config lives at `config.json` inside the selected workspace. Outside `mill init` bootstrap, it must exist and declare `"configFormat":"alpha"`. The alpha config format supports the low-privilege `configFormat` marker plus optional non-blank string `"name"` and boolean `"autoStart"` values. Unknown keys are ignored for compatibility; when config is read during Weaver startup, its parsed unknown-key warnings are emitted to the Mill log with the config file and key names. Ordinary config reads for status and invoke retain those warnings but do not log them. Missing config, malformed config, missing/unsupported config format, or wrong value types for known keys fail non-zero. `config.json` is shareable checked-in workspace config and does not store or authoritatively supply the Millstrand source checkout path.
- **SPEC-002.C2a:** A machine-local `config.local.json` may sit beside `config.json` as a shallow overlay of the optional key (`"name"`; it must not carry `configFormat`). A missing overlay contributes nothing. Unknown overlay keys, including `"autoStart"`, are ignored for compatibility; startup emits their retained warnings to the Mill log with the local config file and key names, while ordinary status and invoke reads do not log them. A malformed present overlay, the known misplaced `configFormat` key, or a wrong value type for a known key fails non-zero. Overlay values win over `config.json`.
- **SPEC-002.C3:** Mill owns Millstrand source checkout resolution for launching the Weaver and its thin nREPL attach client. The resolved source supplies one reserved `io.millstrand/millstrand` coordinate. Workspace `deps.edn` and `deps.local.edn` cannot redeclare or override it; such a declaration fails before resolution. Mill never persists its resolved source path in workspace configuration.
- **SPEC-002.C4:** Public strand/mill commands emit JSON machine output (`strand` responses as NDJSON; a single result is one JSON line) unless a clause explicitly declares direct prose or REPL relay (`mill prime millstrand`, `mill changelog`, and `mill weaver repl`). `--format` and config-file output format settings are not supported. All `strand` JSON output is byte-faithful — single-result stdout, stream-relay lines, and the `details=` JSON appended to stderr error messages are emitted without HTML escaping (`<`, `>`, `&` print literally, never `<`). The `details=` clause binds the **plain** error rendering, which is what stderr gets whenever it is not a terminal and no `MILLSTRAND_ERROR_FORMAT` override selects otherwise (SPEC-002.C4b); the terminal rendering (SPEC-002.C4b) is exempt from it, and no machine consumer is ever handed one.
- **SPEC-002.C4a:** Public CLI op result objects accrete under their published op name: fields may be added, but existing fields are never removed, renamed, retyped, or repurposed. Consumers must ignore unknown fields. An op's `:returns` declaration describes the current producer shape; it does not narrow future results to exactly those fields.
- **SPEC-002.C4b (error rendering modes):** Both binaries use the same plain, pretty, and JSON error renderer. Character-device detection on the stream being written selects pretty for terminals and plain for pipes, files, and captured output; detection never selects JSON. `MILLSTRAND_ERROR_FORMAT=json|plain|pretty` overrides detection, while any other value fails non-zero and names the accepted set. Local-only `--version` and `--help` paths run before this validation (SPEC-002.C34). `NO_COLOR` removes ANSI colour without changing layout. There is no format flag or config setting, and the pretty layout is internal (SPEC-002.C4, SPEC-005.C8).
- **SPEC-002.C4c (client-side error taxonomy):** Client rendering adds `cli` to the wire envelope's `domain|protocol|transport` types (SPEC-004.C24). `cli` identifies a bad local invocation and is never accepted from the wire; unreachable or stale mill state, version skew, and malformed response frames are `transport`. Plain `cli` errors are `error: <message>` with no type, code, or details, and pretty headlines for all locally raised errors omit their synthesized code. Local codes use the informative, non-contractual `cli/` namespace; renderers do not otherwise branch on codes or `:reason` (SPEC-005.C7). The sole named exception is `database/not-initialized`, whose plain form is the bare remediation message.
- **SPEC-002.C4d (did-you-mean suggestions):** Pretty rendering may suggest up to three values from an error's `available` list. It compares names case-insensitively at Levenshtein distance two or less, orders by distance then producer order, and suggests nothing for an exact match. It finds the candidate token from, in order, a details value quoted by the message, the last argv token, or remaining details values in key order; the last tier is used only when all matching candidates agree. Suggestions do not change plain output or the wire frame.
- **SPEC-002.C4e (JSON error mode):** `MILLSTRAND_ERROR_FORMAT=json` writes exactly one newline-terminated, byte-faithful JSON object to stderr with `type`, `code`, `message`, and `details`; all four fields are present and `details` is always an object. It has no prose prefix or folded details. `type` uses SPEC-002.C4c's four-value client taxonomy; `code` is informative and non-contractual (SPEC-005.C7). No other guidance reaches stderr in this mode. `mill bin` failures retain their structured envelope (SPEC-002.C54/C55), exit codes remain unchanged, and interrupts still write nothing and exit 130 (SPEC-002.C36).
- **SPEC-002.C30:** `strand [flags] <op-name> [args...]` stops dispatcher flag parsing at the first non-flag token; the op name resolves against the weaver op registry and everything after it ships verbatim as string argv. The dispatcher parses no per-command flags and interprets no argv values.
- **SPEC-002.C31:** Selection/context precedence: `--workspace` wins outright; otherwise explicit `--worktree-root`/`--git-common-dir` win over derivation; derivation runs from the effective cwd (`--cwd` when given, else process cwd) and fills only unset fields. Failed git derivation with nothing pinned fails loudly with remediation.
- **SPEC-002.C32:** Named payloads: `--stdin` reads stdin verbatim to EOF into payload slot `stdin` (opt-in only; the bin never auto-consumes a pipe); `--payload name=path` reads the named file client-side into a named slot. Duplicate slot names fail loudly before transport. The weaver never reads client-named paths.
- **SPEC-002.C33:** `--timeout <dur>` parses Go-duration style and rides in the envelope as milliseconds so the weaver can cancel or refuse; the invoked leaf's deadline class supplies the default for single-result responses (SPEC-004.C26b). Stream-class responses are never server-deadline-bounded; cancellation is client interrupt, which closes the connection and aborts the emitting handler.
- **SPEC-002.C34:** Local-only flags work without any mill or weaver: `strand --version` and `mill --version` print one JSON object with exactly `version`, `build_id`, and `protocol_version`. Both binaries in one build report the same values. `version` is the product release read from the retained source's root `VERSION` file at build time; `build_id` identifies the full source revision independently and appends `-dirty` for local builds with uncommitted or untracked content; `protocol_version` remains the wire-compatibility key. `strand --help` / `-h` (and bare `strand`) prints static usage covering dispatcher flags, the envelope contract, the environment variables that select the error rendering (SPEC-002.C4b), the live `strand help` pointer, and `mill start` remediation; `--dry-run` prints the assembled request frame instead of sending — the standard frame shape (SPEC-002.C35) with `operation` `"invoke"`, the envelope as `arguments`, empty `options`, and the placeholder `"<dry-run>"` for both `request_id` and `weaver_id`.
- **SPEC-002.C35:** The socket request frame retains protocol version, request id, and weaver id (SPEC-004.C23); the invoke envelope rides as the operation arguments: `{name, argv, payloads, cwd, worktree_root, git_common_dir, workspace, timeout?, is_tty, tty_col, client{pid, version, build_id}}`. `is_tty` reports whether strand stdout is a terminal. `tty_col` is a positive terminal width when `is_tty` is true and `null` otherwise; a terminal whose width cannot be read uses 80 columns. Automatic fields (frame identity, client pid/product version/build identity, terminal capabilities) are not flag-settable.
- **SPEC-002.C36:** Response relay is frame-driven: a single-result response prints the result as one JSON line; a stream response (header frame, emitted NDJSON lines, terminator frame) relays each emitted line as received with per-line flush and exits by the terminator's success flag. Exit codes are contract: `0` on success, non-zero on any error, and `130` on client interrupt — including interrupt during a stream, which exits cleanly after closing the connection.
- **SPEC-002.C37:** Payload references (`:stdin` / `:payload/<name>` as whole argv values) are resolved weaver-side by the blessed parser (`millstrand.api.cli.alpha`, SPEC-003), never by the bin.
- **SPEC-002.C38:** Unknown op names fail non-zero with the weaver's not-found domain error carrying available op names. Malformed dispatcher flags, duplicate payload slots, no reachable mill, no running weaver, stale metadata/socket state, transport/identity failures, malformed weaver responses, database/domain errors, op arg-spec parse failures, and lifecycle hook rejections fail non-zero. Hook failures use the `hook/failed` domain error code with structured details.
- **SPEC-002.C39:** Live discovery is the core-registered `help` op, expressed as one declared, versioned schema, uniformly projected — renderings are transforms over it, and no op hand-authors usage or dispatch output. `strand help <op>` returns one response envelope, never a bare node, with stable top-level `{schema-version, operation, source, glossary, node}` (shape in SPEC-002.C44; runtime machinery in SPEC-004.C106–C112). `schema-version` versions the help-schema contract itself, independent of `protocol_version`; additive accretion does not bump it and a breaking reshape does. The node is fractal and self-similar. `strand help <op> <verb> [<verb> ...]` slices to any declared node at arbitrary depth and returns the same shape under `node`. Removing the raw-envelope operation fact and invocation mode bumps `schema-version` to 3. The node's `returns` carries the JSON-safe return-shape explanation. `strand help` with no op returns versioned `{schema-version, ops[]}`. Two builtin meta-verbs join `help`: `strand about <op>` and `strand prime <op>`. Projection, rendering, source resolution, and the `--help` rewrite are weaver-side; the dispatcher relays verbatim argv and returned bytes without interpreting declarations.
- **SPEC-002.C44 (fractal node + versioned catalog):** The help envelope's `node` is normalized and self-similar; every key is always present with defined empty/null semantics so one recursive renderer needs no per-level branches: `name` (string), `doc` (string, `""` when undeclared), `invocation` (`{mode, flags[], positionals[]}` where `mode` is `"declared"`), `returns` (return-shape explain or `null`), `hook-class` and `deadline-class` (class-name strings on invocable leaves; `null` on interior nodes and subcommand-op roots), `use-when`/`notes` (string arrays, `[]` when none), `failure-modes` (array of glossary outcome names only, `[]` when none), and `children` (node array of the same shape, `[]` for leaves). `operation` carries only `{name, provenance, stream?}`; `source` remains the op-wide handler pointer and `glossary` the referenced-outcome closure. Catalog summary nodes follow the same leaf rule: classes are populated only when the summary node is itself a leaf. Per-entry catalog envelopes still omit `schema-version` and `glossary`.
- **SPEC-002.C45 (default rendering, `--json` floor, verbatim relay):** With no registered default help transform, `strand help` output IS the raw canonical envelope JSON. A registered default help transform (SPEC-004.C106) receives the **full envelope** plus the invoke envelope's terminal capabilities as `{:is-tty boolean, :tty-col positive-integer-or-nil}` and renders help instead; its output is relayed **verbatim** — the weaver's single-result success frame carries an optional `verbatim` boolean (present/`true` only for a transform-rendered `help` result) and the `strand` client then writes the raw string bytes (single trailing newline if absent) rather than the default byte-faithful JSON relay (SPEC-002.C4/C36); absent (the default) means the ordinary JSON relay, a backward-compatible frame extension. `--json` is the **sole**, **leading-only** opt-out back to the raw envelope and the raw floor when no transform is registered; it always bypasses, so a failing transform never bricks help (the failure surfaces loudly, SPEC-004.C106). The per-invocation `-t/--transform` selector is **not shipped**; other flags on the help surface are invalid (`strand help ... --foo` fails). `about`/`prime` output (JSON objects) is never transformed and never verbatim.
- **SPEC-002.C46 (`--help` grammar + `about`/`prime` meta-verbs):** After an op name, `--help`/`-h` is sugar the weaver rewrites to the `help` op, valid **only** as the final token with no other flags or attached payloads; any other shape (`strand agent --foo --help`, a non-final `--help`) is a concise redirect error pointing at `strand help ...`. This trailing-`--help` rewrite applies to **all** ops (flat or subcommand) and supersedes the retired subcommand-only sole-token `<op> help|about|prime` sugar, which is migration-only and retired in alpha (TEN-000@1) — a bare `help`/`about`/`prime` word in verb position fails with the loud redirect (exemption for ops still declaring a real subcommand by that name: SPEC-004.C108). Two builtin meta-verbs join `help`: `strand about <op>` returns `{"about": <prose>, "source": <source>}` and `strand prime <op>` returns `{"prime": <prose>, "source": <source>}` — each a JSON object (never a bare string) with the op-wide `source`. Both are **arity-1** (op-level): a verb path (`strand about agent delegate`) fails loudly and redirects to `help`. Absence of declared `about`/`prime` prose returns a loud `discovery/unavailable` outcome (TEN-003), never empty success.
- **SPEC-002.C47 (dispatcher pre-op `--help` grammar):** `strand --help` / `-h` / bare `strand` with **no op** stays dispatcher usage printed by the Go dispatcher (SPEC-002.C34/C15). Once an op is named (arity ≥ 1), `--help` **must trail**: `strand --help <op>` is now an **error** (was static usage — the dispatcher set the help bit on any pre-op `--help` and ignored trailing tokens). The dispatcher distinguishes no-op `--help` (usage) from op-present pre-op `--help` (error redirecting to `strand help <op>` or a trailing `--help`), and still ships verbatim argv and interprets no arg-spec (SPEC-002.C30, TEN-006).

## SPEC-002.P4 Mill contracts

SPEC-002.C56-C59 are shipped. Mill owns the restart transition, admission gate,
and replacement coverage described by those clauses; the implementation lives
in the Mill CLI and its focused lifecycle and acceptance tests.

- **SPEC-002.C14a:** `mill init` is the selected workspace bootstrap command only. Except for the bootstrap-only `--auto-start` flag, it never contacts a weaver, initializes SQLite storage, or runs `git init`; `--auto-start` requires a running Mill and launches the selected workspace's Weaver as specified by SPEC-002.C61. Without `--workspace`, it creates `.millstrand` when no accepted marker exists or completes the one accepted marker (`.millstrand` or `.ms`) at the canonical Git repository root, and fails loudly outside supported Git layouts. With explicit `--workspace`, it bootstraps that directory directly as an isolated workspace. Bootstrap creates only missing files: selected workspace, `config.json`, `deps.edn`, `init.clj`, `me/help.clj`, and `.gitignore`; it never overwrites existing files. It does not create an empty `spools/` directory; workspace-owned code normally uses a `:file` module. Created config uses only `"configFormat":"alpha"` and does not persist source. Generated `deps.edn` declares the Batteries library with the pinned coordinate owned by the template. The selected workspace's `.gitignore` ignores only the local overlays: `config.local.json`, `deps.local.edn`, and `init.local.clj`. Generated `init.clj` requires `millstrand.api.current.alpha` and `millstrand.api.runtime.alpha`, captures `(current/runtime)`, declares Batteries as a required namespace module, then activates the generated `me/help.clj` file module after Batteries. The adapter registers Batteries' builtin default help transform so fresh workspaces render `strand help` as text while `strand help --json` remains raw. Deleting the Batteries dependency and its activation is the supported opt-out. Repo-world bootstrap (no `--workspace`) additionally ensures the repository-root agent guidance file carries a marker-guarded `## Millstrand / strand` section pointing new agents at `mill prime millstrand` and `strand --help`: it appends the section to whichever of `AGENTS.md`/`CLAUDE.md` exist (idempotent via the `<!-- mill:millstrand-prime -->` open marker with a matching `<!-- /mill:millstrand-prime -->` close marker bounding the block, append-only, never rewriting existing prose) and creates `AGENTS.md` when neither exists. Explicit `--workspace` bootstrap performs no guidance injection.
- **SPEC-002.C14b:** `mill init --stealth` is the explicit exception to C14a's repository guidance injection. It is valid only without
  `--workspace` and may be combined with `--auto-start`; it selects the canonical Git-root `.millstrand` or `.ms`. Before writing anything, it refuses tracked `.millstrand` or `.ms` paths and malformed
  mill-owned marker blocks. It bootstraps ordinary workspace files without editing shared `AGENTS.md` or `CLAUDE.md`, then maintains this
  exact block in `.git/info/exclude`: `# mill:millstrand-stealth`, `/.millstrand`, `/.ms`, `/CLAUDE.local.md`, `# /mill:millstrand-stealth`. It maintains the
  exact C14a guidance block in an untracked `CLAUDE.local.md`; a tracked `CLAUDE.local.md` is left untouched. An absent owned file is
  created with the exact block. A non-empty marker-free file keeps its bytes and gains a separating newline plus the block. Exact blocks,
  including their final newline, are unchanged; partial, duplicate, reordered, or edited blocks are semantic refusals. The existing `config_dir` and
  `config_file` success keys gain a typed `stealth` object with closed `git_exclude` (`path`, `status`), `claude_guidance` (`path`,
  `status`), and `codex_guidance` (`status`, `suggested_text`) children. File status values are `created`, `updated`, `unchanged`, and,
  for Claude guidance only, `skipped-tracked`; Codex status is `manual-required`. Go response structs validate this shape before emission.
  Semantic refusals use code `mill/init-stealth-refused` and exactly `path`, `target`, `state`, and `remediation` details. Target values are
  `tracked-millstrand`, `git-exclude`, and `claude-guidance`; state values are `tracked`, `start-only`, `end-only`, `duplicate-start`,
  `duplicate-end`, `reversed`, and `edited`. Ordinary `mill init` output remains unchanged.
- **SPEC-002.C15:** `mill` uses Cobra for its command tree and help text. The `strand` dispatcher owns its fixed flag set directly and must clearly describe the dispatcher contract in `--help`; it has no command tree to document.
- **SPEC-002.C15a (mill failure output):** A failed `mill` invocation prints exactly one error rendering (SPEC-002.C4b), then only the guidance its failure class earns. An unknown command adds a single pointer at `--help` for the command Cobra did resolve. A malformed invocation — a flag Cobra cannot parse, or an argument count a command rejects — adds that command's usage block. Both classes are recognised structurally, never by matching error text. A command that ran and failed adds neither: a flag list explains nothing about an unreachable weaver. `mill bin` failures stay the structured JSON envelope alone (SPEC-002.C54/C55) and gain no guidance. Neither does any failure under `MILLSTRAND_ERROR_FORMAT=json`: the envelope line is the whole of stderr, with no usage block and no `--help` pointer after it (SPEC-002.C4e).
- **SPEC-002.C16:** `mill weaver start` resolves the selected workspace and source, requires the source's canonical `VERSION` to match the product version stamped into Mill, composes one tools.deps generation basis from required `deps.edn`, optional `deps.local.edn`, selected `:millstrand/weaver` then `:millstrand/local` aliases, and Mill's reserved runtime coordinate, then starts the Weaver in that basis. It supplies the same expected product version to the Weaver, which verifies the retained source again before startup. It never composes an enclosing project or user dependency source. The retained name, timeout, log, storage, startup-file order, and orphan-prevention contracts remain unchanged.
- **SPEC-002.C17:** `mill weaver repl` is the public path for users who need to run trusted spool-workspace Clojure code. It verifies the selected workspace's weaver is running and attaches to its nREPL endpoint using mill-resolved source launch context. Mill does not proxy nREPL traffic. Any launched local process is a thin transport/UI attach client only; user forms evaluate in the weaver JVM.
- **SPEC-002.C17a:** `mill prime millstrand` prints harness-agnostic agent context to stdout and needs no running mill or weaver. It resolves the Millstrand source with SPEC-002.C3 precedence and prints exactly two newline-terminated labeled absolute paths: `Millstrand source: <resolved-source>` and `Millstrand reference: <resolved-source>/docs/reference.md`, with the reference path assembled for the host filesystem. It carries no independent orientation prose. A missing or non-regular reference file fails non-zero with its path, and an unresolvable source fails non-zero. Use `strand --help` for the CLI orientation that the Go dispatcher owns.
- **SPEC-002.C17b:** `mill changelog` prints the retained source's `CHANGELOG.md` bytes unchanged and needs no running mill or weaver. It resolves the source with SPEC-002.C3 precedence and first validates that source's root `VERSION` is exactly one newline-terminated `MAJOR.MINOR.PATCH` value matching the version stamped into Mill. Missing, mismatched, malformed, non-regular, or empty release files fail non-zero with the path instead of falling back to embedded prose or another checkout.
- **SPEC-002.C18:** `mill weaver repl --stdin` is the public path for agents that need to run trusted spool-workspace Clojure code. It sends stdin Clojure forms to the selected running weaver nREPL for direct evaluation in the weaver JVM, prints one direct normal Clojure result per top-level form, and exits non-zero on read, eval, or transport errors. It does not impose a JSON or EDN response envelope.
- **SPEC-002.C20:** `mill weaver status --json` retains its health, identity, storage, log, pid, socket, and nREPL fields and includes `version`, the product version published by the running Weaver, plus `basis_fingerprint`, the running generation's exact `sha256:<64 lowercase hexadecimal digits>` value. Mill relays both unchanged and never recomputes them. `mill weaver stop` retains its existing ownership and staleness checks.
- **SPEC-002.C20a:** `mill weaver list` returns a JSON array for editor/tooling discovery. Rows include `config_dir`, `state_dir`, `data_dir`, `database_kind`, `database_label`, `database_path`, `name`, `log_path`, and `state`; running rows also include `pid`, `weaver_id`, `socket_path`, `nrepl`, `started_at`, and `version`. The list includes supervised children and metadata-discovered weavers under the mill state root. Missing, malformed, or product-mismatched Weaver versions fail loudly instead of being silently admitted or repaired; align and deliberately restart an older live Weaver rather than treating version-less metadata as compatible.
- **SPEC-002.C20b:** No public CLI command or flag selects weaver storage kind. CLI metadata/status validation compares `database_kind` and `database_label` for all storage kinds and `database_path` only for `sqlite-file`, failing loudly on malformed or inconsistent storage metadata. Mill supervises file-backed workspace weavers only and rejects other storage kinds in mill-managed weaver metadata.
- **SPEC-002.C56 (restart lifecycle):** `mill weaver restart` is the one Mill-owned replacement transition for the selected workspace. Its states are `probing`, `restarting`, `running`, and `failed`; `mill weaver status` reports the current state, selected workspace, opaque `generation_id`, and any active or retained failed transition. `mill weaver restart --json` returns one validated JSON result with `operation`, `workspace`, `state`, `generation_id` when a generation exists, `transition_id` while a transition exists, and structured stage-specific diagnostics for every observable failed transition, as defined by SPEC-004.C113/C113a. A successful restart changes `generation_id` exactly once. A failed probe leaves the old generation running; a failed cutover leaves the workspace `failed` and never readmits the old generation. Concurrent lifecycle callers converge on the active transition, and each caller's readiness timeout starts when it joins without cancelling that shared transition. `start` returns the admitted old generation during `running` or `probing`, joins during `restarting`, and returns a retained failure during `failed`; `restart` creates or joins the replacement transition in every state.
- **SPEC-002.C56a (lifecycle presentation):** `mill start`, `mill status`, and `mill weaver start|status|restart|stop` print readable status to stdout by default. Foreground Mill events and lifecycle progress carry local timestamps. Start, restart, and stop report immediately and periodically while waiting; restart reports observed probe and replacement phases. Status includes the available workspace, process identity, start time, log path, and failure explanation without dumping metadata. ANSI color is limited to stdout terminals, disabled by `NO_COLOR` presence or `TERM=dumb`. `mill status --json` and `mill weaver start|status|restart|stop --json` print one full JSON result without progress; the existing Mill server/client boundary owns result validation. `mill start --json` writes a stream of JSON objects, each with exactly `time` (an RFC 3339 timestamp with timezone) and `message` (human-readable text). Error rendering on stderr and detailed weaver log files retain their existing contracts.
- **SPEC-002.C57 (replacement probe and readiness):** Before closing old-generation admission, restart requires the admitted generation's complete C26 `registry_projection` and a passing fresh-generation probe in a disposable workspace with independent storage, runtime state, basis, and classloader. Missing or malformed evidence fails the probe; Mill never substitutes an empty projection. The probe exercises generation construction and validation without publishing the candidate or running its durable and external effects. Probe and replacement-startup failures retain the actionable stage, log, exit, and workspace evidence that exists for that stage under SPEC-004.C114; a failed probe retains its disposable workspace for inspection. Ready means the replacement request socket accepts calls, startup and module/lifecycle reconciliation have completed, and persistent scheduler rows have rearmed. If Mill cannot confirm that the old generation stopped, restart ends `failed` without launching the replacement.
- **SPEC-002.C58 (Mill admission and one-send boundary):** Mill owns one per-workspace admission gate shared by lifecycle commands and forwarded invocations. Requests may bind to the admitted old generation during `probing`; that binding and the first Weaver socket write share the admission critical section, so closure waits for the write and an old-generation request cannot first send after closure. Once Mill closes admission and records `restarting`, no new request can bind to the old generation. An unadmitted request waits for the shared transition without entering a persistent queue, then sends once to the replacement or returns unsent on failure, deadline expiry, or cancellation. Mill never replays a sent request, including when cutover loses its response. A sent request interrupted by replacement returns `weaver/restarted` or its existing transport outcome. Internal request and response envelopes are closed and validated at decode and encode under SPEC-004.C115. Direct Weaver-socket and nREPL clients remain outside Mill admission and must reconnect after disconnection.
- **SPEC-002.C58a (relay delivery evidence):** Mill records request delivery separately from response delivery. A response counts only after at least one complete newline-delimited frame is read; an unterminated or otherwise partial response at EOF is a transport failure, even when request delivery is possible, and the request is never replayed.
- **SPEC-002.C59 (restart scope):** Restart continuity covers an ordinary planned replacement while the same Mill remains alive. Sent requests are never replayed, mutations are never reissued automatically, and Mill promises neither exactly-once external effects nor recovery across its own replacement or exit. Sent streams and awaits interrupted by replacement return `weaver/restarted`; an owning spool or client may explicitly rearm a safe read from durable state.
- **SPEC-002.C60 (autostart config):** The selected workspace's shared `config.json` may contain the optional `autoStart` key, whose value must be a JSON boolean. `config.local.json` has no supported `autoStart` setting; a local key with that name is unknown and is ignored with the startup warning described by SPEC-002.C2a. The local overlay has no equivalent opt-in. Omitted and `false` values both mean that the workspace is not eligible for remembered startup.
- **SPEC-002.C61 (autostart registration):** `mill init --auto-start` requires a running Mill. It writes `"autoStart": true` to the selected shared `config.json` and records a true Mill-owned remembered-start registration before starting the selected workspace's Weaver immediately. Mill transport and Weaver start failures are returned normally; init has no offline registration fallback. Without `--auto-start`, ordinary init behavior is unchanged. `mill weaver start` records a true registration before returning only when the selected shared `config.json` already has `"autoStart": true`, including when the selected workspace's Weaver is already running, and does not add `autoStart` to `config.json`. With `autoStart` omitted or false, explicit start never registers.
- **SPEC-002.C62 (startup pruning):** When Mill starts, it re-reads each remembered registration's selected shared `config.json` before attempting a start. It prunes registrations whose config omits `autoStart` or sets it to `false`, then attempts the remaining eligible registrations. A registration pruned during that startup is not rediscovered merely because its config later changes to `autoStart: true`. An explicit `mill weaver start` creates a registration only when shared `autoStart` was already true; false or omitted explicit starts never register, including if the config later changes to true. `mill weaver start` or `mill init --auto-start` must register it again.
- **SPEC-002.C63 (bounded restoration):** Mill starts eligible remembered workspaces with at most four starts in flight. Before launching each Weaver or waiting for its readiness, it writes an autostart progress log naming the workspace and announcing the start attempt; the contract does not require an attempt identifier or counter. Each eligible registration gets one start attempt per Mill boot. Mill logs that start and any failure, releases the workspace's start slot on every outcome, and continues with other eligible registrations after an individual failure. Restoration does not add a retry queue or alter Weaver readiness, source resolution, naming, or restart semantics.
- **SPEC-002.C64 (registration storage):** Remembered-start registrations are Mill-owned state under the existing XDG state root. Their physical files and log format are internal; no workspace overlay or second user-facing registration file is part of the CLI contract.
- **SPEC-002.C48 (mill bin boundary):** `mill bin list`, `mill bin build <bin>`, and `mill bin run <bin> [args...]` are client-side Mill verbs over the live Weaver's read-only `bins` op. Bin list and plan requests are non-interactive invokes (`is_tty=false`, `tty_col=null`); a build or run process inherits the caller's terminal as specified below. `strand` has no bin execution path and remains a pure dispatcher.
- **SPEC-002.C49 (bin list):** `mill bin list` relays the `bins list` result as one JSON object. The result contains the effective winning declarations after owner and override resolution. An empty `:bins` registry returns an empty `bins` collection. The command does not inspect the filesystem and does not start a process.
- **SPEC-002.C50 (bin run):** `mill bin run <bin> [args...]` requires a runnable plan and passes every trailing argument unchanged after the resolved executable. Mill flag parsing stops at `<bin>`, so Mill flags, including `--workspace`, precede it. The bin replaces Mill, preserves the caller's cwd, and inherits stdin, stdout, stderr, controlling terminal, session, and foreground process group. Success emits no Mill result.
- **SPEC-002.C51 (bin build):** `mill bin build <bin>` requires a declared build recipe, runs its argv in its declared cwd with the caller's stdin, stdout, and stderr, waits for exit, and emits the JSON build result. A missing recipe is `bin/no-build-recipe`; a process that cannot start is `bin/build-start-failed`; a non-zero child exit is `bin/build-failed`. Re-running the recipe is the recovery path; Mill keeps no completion stamp or build lock.
- **SPEC-002.C52 (bin plan contract):** A bin plan carries `bin` (string), `runnable` (boolean or null), `exec` (object), and optional `build` (object). `exec` carries exactly one of `path` (canonical absolute string) or `command` (unchanged bare name), plus an `env` string-to-string overlay. `build`, when present, carries `argv` (non-empty string vector) and `cwd` (absolute string). Malformed or contradictory plans fail rather than falling back.
- **SPEC-002.C53 (bin environment):** Mill composes the child environment from the caller's complete environment plus the plan's `exec.env` overlay. The overlay contains `MILLSTRAND_WORKSPACE`, set to the selected workspace path. It carries no run id, weaver id, or peer name. The plan does not echo the caller's cwd or environment. A wrapper reads `MILLSTRAND_WORKSPACE` when it needs to invoke ordinary `strand` ops against the selected world.
- **SPEC-002.C54 (bin outcomes):** The build success result is a JSON object with operation `bin build`, the bin name, the child exit code, and elapsed milliseconds. `bin run` reports no success envelope because mill has been replaced by the executable. Every lookup, planning, relay, build, and exec failure is a structured non-zero object with `operation` and `error`, plus `bin` once its name is known. Locally constructed client, transport, malformed-plan, build-start, and exec failures carry `cause`; build-start and build-exit failures carry `argv`; not-runnable and exec failures carry `path`. Mill adds no uniform remediation or value field.
- **SPEC-002.C55 (bin failure outcomes):** `bin/unknown` means no active declaration has the name; `bin/anchor-unresolved` means a `:family` or `:root` anchor cannot resolve from the declaring file; `bin/not-built` means a declared build recipe has a false runnable predicate; `bin/not-runnable` means a buildless bin has a false predicate; `bin/no-build-recipe` means build was requested without a recipe; `bin/build-start-failed`, `bin/build-failed`, and `bin/exec-failed` describe the corresponding host process failures. A bare command has `runnable` null, so mill attempts it and reports an exec failure only if the host cannot start it.

## SPEC-002.P5 Transport and security boundaries

- **SPEC-002.C41:** Dispatcher requests carry one bounded envelope. Bounded bulk input is an explicit payload parsed and applied op-side in one transaction; unbounded live ingestion belongs inside the Weaver, not in a dispatcher flag.
- **SPEC-002.C42:** No public CLI surface bypasses lifecycle hooks.

## SPEC-002.P6 Deferred

The public CLI is limited to Mill bootstrap, supervision, trusted REPL attach, changelog and bin execution, plus dispatch of registered Weaver ops. Runtime authoring and extension remain trusted workspace, API, spool, and REPL concerns.
