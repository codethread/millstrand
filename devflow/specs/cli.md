# CLI Surface

**Document ID:** `SPEC-002` **Status:** Implemented **Last Updated:** 2026-08-18 **Related RFCs:** [RFC-019 Op-only CLI](../archive/26-07-04__op-only-cli/rfcs/2026-07-04-op-only-cli.md), [RFC-002 Task Query DSL](../rfcs/2026-06-24-task-query-dsl.md), [RFC-003 Fast JSON Socket CLI](../archive/26-06-25__go-cli-migration/rfcs/2026-06-25-fast-json-socket-cli.md), [RFC-004 Go CLI Migration](../archive/26-06-25__go-cli-migration/rfcs/2026-06-25-go-cli-migration.md) **Code:** `cli/`, `src/millstrand/core/weaver`, `src/millstrand/api/weaver/alpha.clj`, `.millstrand/workflows.clj` (this repository's coordination workspace; application workspaces use `.millstrand` or `.ms`)

## SPEC-002.P1 Purpose

The public CLI is two thin Go binaries. `mill` owns routing and supervision, workspace bootstrap, weaver lifecycle, trusted nREPL attach, and client-side execution that must preserve the caller's terminal, cwd, and environment. `strand` remains a pure dispatcher for registered weaver ops: it resolves selection context, assembles one invoke envelope per call, and relays NDJSON back. `strand` has **zero builtin subcommands**: every command name is a weaver-registered op (SPEC-004.C63a–c). The shipped everyday command surface (`add`, `list`, `ready`, `weave`, ...) is registered by the `millstrand.spools.batteries` reference spool, and its per-command behavior contract lives at [`spools/batteries.md`](../../spools/batteries.md), not in this spec. Other activated reference spools register their own ops and document their per-op contracts in their spool docs.

CLI/agent list-style reads are lean and capped by default. The `list`, `ready`, and query-backed listing surfaces return an omission descriptor for attribute values above the fixed byte floor, while `show` returns the full row. Those listing surfaces also apply a default result cap of 500 before attribute assembly. If more rows match, the op fails instead of returning a partial result; the error names the total, the cap, and the remedies: narrow with `--query`/`--param`/`--state`, or pass explicit `--limit N`. Setting `--limit` above the reported total is the sanctioned full read. No pagination is part of the CLI contract; a capped-out consumer should write a narrower query. No hydration flag is part of the CLI surface; callers compose a lean listing with `show <id>` when they need a large payload. The dispatcher still relays op output verbatim as NDJSON; leanness and result caps are batteries read-surface transforms, not transport behavior.

## SPEC-002.P2 Interface

Entrypoints:

```text
strand [dispatcher-flags] <op-name> [args...]
strand --help | -h | --version
strand --dry-run [dispatcher-flags] <op-name> [args...]

mill start
mill status
mill weaver list
mill init [--workspace <dir> | --stealth]
mill weaver start [--workspace <dir>] [--name <name>] [--ready-timeout <dur>]
mill weaver status|stop [--workspace <dir>]
mill weaver repl [--stdin] [--workspace <dir>]
mill prime millstrand
mill bin list
mill bin build <bin>
mill bin run <bin> [args...]
```

Dispatcher flags: `--workspace <dir>`, `--cwd <dir>`, `--worktree-root <dir>`, `--git-common-dir <dir>`, `--stdin`, `--payload name=path` (repeatable), `--timeout <dur>`, `--dry-run`, `--version`, `--help` (`-h` is an equivalent top-level alias).

## SPEC-002.P3 Dispatcher contracts

- **SPEC-002.C1:** Public `strand` commands require a reachable local `mill` entrypoint. If no mill is running or its metadata/socket is stale, commands fail non-zero with remediation to run `mill start`. If a live mill's metadata carries a different mill protocol version than the invoking `strand` binary, commands fail non-zero naming both protocol versions, both build identities when stamped, and the metadata path, with remediation to align versions (rebuild `strand` to match the running mill, or restart mill from the newer build) — never the `mill start` remedy, which is misleading while a mill runs.
- **SPEC-002.C1a:** `--workspace` selects a Millstrand workspace and is the highest-precedence override. Without it, implicit repo selection requires cwd to be inside a supported non-bare Git worktree; the selected workspace is the canonical repository `.millstrand` or `.ms` directory derived from the absolute Git common directory. Linked worktrees for one repository therefore select the same default workspace. The unsupported legacy workspace name is rejected as an application marker. Outside supported Git layouts, no-flag commands fail loudly rather than creating cwd workspaces. Runtime state, sockets, metadata, and SQLite data live under mill-owned XDG state paths, not inside the selected workspace.
- **SPEC-002.C2:** Client JSON config lives at `config.json` inside the selected workspace. Outside `mill init` bootstrap, it must exist and declare `"configFormat":"alpha"`. The alpha config format supports the low-privilege `configFormat` marker plus an optional non-blank string `"name"` declaring the workspace's portable logical weaver name; missing config, malformed config, missing/unsupported config format, unsupported keys, or wrong value types fail non-zero. `config.json` is shareable checked-in workspace config and does not store or authoritatively supply the Millstrand source checkout path.
- **SPEC-002.C2a:** A machine-local `config.local.json` may sit beside `config.json` as a shallow overlay of the optional keys (`"name"`; it must not carry `configFormat`). A missing overlay contributes nothing; a malformed present overlay, unknown overlay keys, or wrong value types fail non-zero. Overlay values win over `config.json`.
- **SPEC-002.C3:** Mill owns Millstrand source checkout resolution for launching the weaver and any thin nREPL attach client used by `mill weaver repl`. It resolves source from `MILLSTRAND_SOURCE`, then install-time embedded source, then a canonical Millstrand checkout cwd containing `deps.edn`; failures are non-zero and actionable. Source is launch context, not selected workspace identity or config workspace state.
- **SPEC-002.C4:** Public strand/mill commands emit JSON machine output (`strand` responses as NDJSON; a single result is one JSON line). `--format` and config-file output format settings are not supported. All `strand` JSON output is byte-faithful — single-result stdout, stream-relay lines, and the `details=` JSON appended to stderr error messages are emitted without HTML escaping (`<`, `>`, `&` print literally, never `<`). The `details=` clause binds the **plain** error rendering, which is what stderr gets whenever it is not a terminal and no `MILLSTRAND_ERROR_FORMAT` override selects otherwise (SPEC-002.C4b); the terminal rendering (SPEC-002.C4b) is exempt from it, and no machine consumer is ever handed one.
- **SPEC-002.C4a:** Public CLI op result objects accrete under their published op name: fields may be added, but existing fields are never removed, renamed, retyped, or repurposed. Consumers must ignore unknown fields. An op's `:returns` declaration describes the current producer shape; it does not narrow future results to exactly those fields.
- **SPEC-002.C4b (error rendering modes):** One renderer formats every error either binary writes. Three renderings ship: **plain**, the single `error: ...` line SPEC-002.C4 pins; **pretty**, an expanded terminal layout over the same fields — it reformats them and may rank what they already carry (SPEC-002.C4d), but invents no fact of its own; and **json**, the error envelope as one decodable line for a caller composing over the CLI (SPEC-002.C4e). Selection is by character-device detection against the stream actually being written, so pipes, files, and captured subprocess output all get plain. `MILLSTRAND_ERROR_FORMAT` overrides the detection; the accepted set is `json|plain|pretty`, and any other value fails non-zero naming the accepted set rather than falling back to one. Detection only ever picks plain or pretty: `json` is reached by name alone. Both binaries validate it once at entry, after the local-only paths SPEC-002.C34 promises work with no weaver, so a typo cannot take down `--version` or `--help`. Selection is by environment variable only: there is no `--format` flag and no config-file setting (SPEC-002.C4). `NO_COLOR` suppresses ANSI colour and changes no layout. The pretty layout itself stays internal (SPEC-005.C8).
- **SPEC-002.C4c (client-side error taxonomy, and the one code the renderer knows):** The renderer's taxonomy carries four values: the three the wire envelope declares (`domain`, `protocol`, `transport`, SPEC-004.C24) plus `cli` for an error a bin raises about its own invocation. `cli` is synthesized client-side and never parsed — the wire envelope keeps exactly three types, and a frame claiming `cli` stays invalid. A local failure to reach the mill (unreachable, stale metadata, protocol skew) is `transport`; only a bad invocation is `cli`. Plain rendering of a `cli` error is the bare `error: <message>` line: no type noun, no code, no `details=`, and the pretty headline of any locally raised error prints no code either — a code a bin synthesized for itself is for a decoder, not a reader. JSON mode (SPEC-002.C4e) carries the same four values in its `type` field, a response frame that will not decode included: that is skew between the bin, the mill, and the weaver, so it is `transport`. Locally raised errors carry informative codes in a `cli/` namespace which, like every code outside the three SPEC-005.C7 pins, may change and must never be branched on. Rendering is otherwise affordance-driven and switches on no error code and no `:reason` — codes outside the pinned three are explicitly non-contractual (SPEC-005.C7) and `:reason` has no registry, so branching on either would break for every spool-authored op. The single exception is `database/not-initialized`, whose plain rendering stays the bare message, because that message is the `mill init` remediation users read; it is named here and pinned by a golden test.
- **SPEC-002.C4d (did-you-mean suggestions):** When an error's details carry an `available` list of names, the pretty rendering ranks that list against the token the error is complaining about and prints the near misses above the full list. `available` is a convention any op may follow, including a spool-authored or user-authored one, so the token is found by affordance and never by key name: the details value the message quotes verbatim, then the last argv token, then the remaining details values in key order — the first tier that lands near a name answers. The last tier has no provenance, so it answers only when every one of its candidates that ranks agrees on the same names; two pointing different ways means silence, because metadata sitting two edits from a real name is not evidence of a typo. Matching is case-insensitive Levenshtein at edit distance 2 or less, capped at three names, closest first with the producer's own list order breaking ties; a token already on the list is not a typo and ranks nothing. When nothing ranks, nothing is printed and the list stands alone. Suggestions are pretty-only: plain output stays byte-identical (SPEC-002.C4) and no wire frame changes.
- **SPEC-002.C4e (JSON error mode):** `MILLSTRAND_ERROR_FORMAT=json` makes stderr carry each failure as exactly one JSON object, newline-terminated, with the fields `type`, `code`, `message`, and `details` — all four always present, `details` an object even when the error carried none, so a consumer never tests for absence. There is no `error: ` prefix, no `details=` tail, and no prose folded into `message`: the `available` and `canonical-query` foldings belong to the plain rendering, and a JSON consumer reads those keys out of `details` itself. The line is byte-faithful in the same sense as SPEC-002.C4. `type` is the four-value client taxonomy of SPEC-002.C4c and is the field consumers branch on; `code` is informative and non-contractual (SPEC-005.C7). JSON is never detected — a terminal that did not ask for it still gets pretty — and nothing else reaches stderr in this mode, so the guidance SPEC-002.C15a otherwise grants is suppressed. `mill bin` failures keep their own structured envelope (SPEC-002.C54/C55) in every mode. Exit codes are unchanged (SPEC-002.C36) and an interrupt still writes nothing and exits 130, so a consumer keys interruption off the exit code rather than off a line that never comes.
- **SPEC-002.C30:** `strand [flags] <op-name> [args...]` stops dispatcher flag parsing at the first non-flag token; the op name resolves against the weaver op registry and everything after it ships verbatim as string argv. The dispatcher parses no per-command flags and interprets no argv values.
- **SPEC-002.C31:** Selection/context precedence: `--workspace` wins outright; otherwise explicit `--worktree-root`/`--git-common-dir` win over derivation; derivation runs from the effective cwd (`--cwd` when given, else process cwd) and fills only unset fields. Failed git derivation with nothing pinned fails loudly with remediation.
- **SPEC-002.C32:** Named payloads: `--stdin` reads stdin verbatim to EOF into payload slot `stdin` (opt-in only; the bin never auto-consumes a pipe); `--payload name=path` reads the named file client-side into a named slot. Duplicate slot names fail loudly before transport. The weaver never reads client-named paths.
- **SPEC-002.C33:** `--timeout <dur>` parses Go-duration style and rides in the envelope as milliseconds so the weaver can cancel or refuse; the invoked leaf's deadline class supplies the default for single-result responses (SPEC-004.C26b). Stream-class responses are never server-deadline-bounded; cancellation is client interrupt, which closes the connection and aborts the emitting handler.
- **SPEC-002.C34:** Bin-only flags work without any mill or weaver: `--version` prints one JSON object with exactly `bin_version` and `protocol_version`; `--help` / `-h` (and bare `strand`) prints static usage covering dispatcher flags, the envelope contract, the environment variables that select the error rendering (SPEC-002.C4b), the live `strand help` pointer, and `mill start` remediation; `--dry-run` prints the assembled request frame instead of sending — the standard frame shape (SPEC-002.C35) with `operation` `"invoke"`, the envelope as `arguments`, empty `options`, and the placeholder `"<dry-run>"` for both `request_id` and `weaver_id`.
- **SPEC-002.C35:** The socket request frame retains protocol version, request id, and weaver id (SPEC-004.C23); the invoke envelope rides as the operation arguments: `{name, argv, payloads, cwd, worktree_root, git_common_dir, workspace, timeout?, is_tty, tty_col, client{pid, version}}`. `is_tty` reports whether strand stdout is a terminal. `tty_col` is a positive terminal width when `is_tty` is true and `null` otherwise; a terminal whose width cannot be read uses 80 columns. Automatic fields (frame identity, client pid/version, terminal capabilities) are not flag-settable.
- **SPEC-002.C36:** Response relay is frame-driven: a single-result response prints the result as one JSON line; a stream response (header frame, emitted NDJSON lines, terminator frame) relays each emitted line as received with per-line flush and exits by the terminator's success flag. Exit codes are contract: `0` on success, non-zero on any error, and `130` on client interrupt — including interrupt during a stream, which exits cleanly after closing the connection.
- **SPEC-002.C37:** Payload references (`:stdin` / `:payload/<name>` as whole argv values) are resolved weaver-side by the blessed parser (`millstrand.api.cli.alpha`, SPEC-003), never by the bin.
- **SPEC-002.C38:** Unknown op names fail non-zero with the weaver's not-found domain error carrying available op names. Malformed dispatcher flags, duplicate payload slots, no reachable mill, no running weaver, stale metadata/socket state, transport/identity failures, malformed weaver responses, database/domain errors, op arg-spec parse failures, and lifecycle hook rejections fail non-zero. Hook failures use the `hook/failed` domain error code with structured details.
- **SPEC-002.C39:** Live discovery is the core-registered `help` op, expressed as one declared, versioned schema, uniformly projected — renderings are transforms over it, and no op hand-authors usage or dispatch output. `strand help <op>` returns one response envelope, never a bare node, with stable top-level `{schema-version, operation, source, glossary, node}` (shape in SPEC-002.C44; runtime machinery in SPEC-004.C106–C112). `schema-version` versions the help-schema contract itself, independent of `protocol_version`; additive accretion does not bump it and a breaking reshape does. The node is fractal and self-similar. `strand help <op> <verb> [<verb> ...]` slices to any declared node at arbitrary depth and returns the same shape under `node`. This feature's node/operation reshape bumps `schema-version` once. The node's `returns` carries the JSON-safe return-shape explanation. `strand help` with no op returns versioned `{schema-version, ops[]}`. Two builtin meta-verbs join `help`: `strand about <op>` and `strand prime <op>`. Projection, rendering, source resolution, and the `--help` rewrite are weaver-side; the dispatcher relays verbatim argv and returned bytes without interpreting declarations.
- **SPEC-002.C44 (fractal node + versioned catalog):** The help envelope's `node` is normalized and self-similar; every key is always present with defined empty/null semantics so one recursive renderer needs no per-level branches: `name` (string), `doc` (string, `""` when undeclared), `invocation` (`{mode, flags[], positionals[]}` where `mode` is `"declared"` or `"raw-envelope"`), `returns` (return-shape explain or `null`), `hook-class` and `deadline-class` (class-name strings on invocable leaves; `null` on interior nodes and subcommand-op roots), `use-when`/`notes` (string arrays, `[]` when none), `failure-modes` (array of glossary outcome names only, `[]` when none), and `children` (node array of the same shape, `[]` for leaves). `invocation.mode` distinguishes raw-envelope from declared invocation. `operation` carries only `{name, provenance, stream?, raw-envelope}`; `source` remains the op-wide handler pointer and `glossary` the referenced-outcome closure. Catalog summary nodes follow the same leaf rule: classes are populated only when the summary node is itself a leaf. Per-entry catalog envelopes still omit `schema-version` and `glossary`.
- **SPEC-002.C45 (default rendering, `--json` floor, verbatim relay):** With no registered default help transform, `strand help` output IS the raw canonical envelope JSON. A registered default help transform (SPEC-004.C106) receives the **full envelope** plus the invoke envelope's terminal capabilities as `{:is-tty boolean, :tty-col positive-integer-or-nil}` and renders help instead; its output is relayed **verbatim** — the weaver's single-result success frame carries an optional `verbatim` boolean (present/`true` only for a transform-rendered `help` result) and the `strand` client then writes the raw string bytes (single trailing newline if absent) rather than the default byte-faithful JSON relay (SPEC-002.C4/C36); absent (the default) means the ordinary JSON relay, a backward-compatible frame extension. `--json` is the **sole**, **leading-only** opt-out back to the raw envelope and the raw floor when no transform is registered; it always bypasses, so a failing transform never bricks help (the failure surfaces loudly, SPEC-004.C106). The per-invocation `-t/--transform` selector is **not shipped**; other flags on the help surface are invalid (`strand help ... --foo` fails). `about`/`prime` output (JSON objects) is never transformed and never verbatim.
- **SPEC-002.C46 (`--help` grammar + `about`/`prime` meta-verbs):** After an op name, `--help`/`-h` is sugar the weaver rewrites to the `help` op, valid **only** as the final token with no other flags or attached payloads; any other shape (`strand agent --foo --help`, a non-final `--help`) is a concise redirect error pointing at `strand help ...`. This trailing-`--help` rewrite applies to **all** ops (flat, subcommand, raw-envelope) and supersedes the retired subcommand-only sole-token `<op> help|about|prime` sugar, which is migration-only and retired in alpha (TEN-000@1) — a bare `help`/`about`/`prime` word in verb position fails with the loud redirect (exemption for ops still declaring a real subcommand by that name: SPEC-004.C108). Two builtin meta-verbs join `help`: `strand about <op>` returns `{"about": <prose>, "source": <source>}` and `strand prime <op>` returns `{"prime": <prose>, "source": <source>}` — each a JSON object (never a bare string) with the op-wide `source`. Both are **arity-1** (op-level): a verb path (`strand about agent delegate`) fails loudly and redirects to `help`. Absence of declared `about`/`prime` prose returns a loud `discovery/unavailable` outcome (TEN-003), never empty success.
- **SPEC-002.C47 (dispatcher pre-op `--help` grammar):** `strand --help` / `-h` / bare `strand` with **no op** stays dispatcher usage printed by the Go dispatcher (SPEC-002.C34/C15). Once an op is named (arity ≥ 1), `--help` **must trail**: `strand --help <op>` is now an **error** (was static usage — the dispatcher set the help bit on any pre-op `--help` and ignored trailing tokens). The dispatcher distinguishes no-op `--help` (usage) from op-present pre-op `--help` (error redirecting to `strand help <op>` or a trailing `--help`), and still ships verbatim argv and interprets no arg-spec (SPEC-002.C30, TEN-006).
- **SPEC-002.C39a:** The repo coordination workspace's `land` op enriches every
  checkpoint view in the `:ready` collection returned by `start`, `ready`,
  `complete`, `choose`, and `status` with `:choice-details` beside `:choices`.
  The value is the canonical string-keyed `workflow/choice-details` map for
  that materialized step, including its declared input contract and route. Each
  checkpoint is joined by its own step id; non-checkpoint views omit the field.
  The shared workflow step-view remains unchanged.
- **SPEC-002.C39b:** The repo coordination workspace's `land` op requires `strand land choose <land-run-id> approved` for approved sign-off; generic workflow approval is vetoed before commit. Sign-off batches must attribute every updated workflow root row to exactly one distinct usable run id; missing, malformed, or multiple attributions fail with `land/signoff-run-ambiguous`. Malformed active merge-lock ownership metadata fails with `land/merge-lock-corrupt`, duplicate active merge locks fail with `land/multiple-merge-locks`, and an approved sign-off without its matching merge lock fails with `land/signoff-without-merge-lock`.

## SPEC-002.P4 Mill contracts

- **SPEC-002.C14a:** `mill init` is the selected workspace bootstrap command only. It creates or completes missing alpha workspace files/directories and never contacts a weaver, initializes SQLite storage, or runs `git init`. Without `--workspace`, it creates `.millstrand` when no accepted marker exists or completes the one accepted marker (`.millstrand` or `.ms`) at the canonical Git repository root, and fails loudly outside supported Git layouts. With explicit `--workspace`, it bootstraps that directory directly as an isolated workspace. Bootstrap creates only missing files: selected workspace, `config.json`, `spools.edn`, `init.clj`, `me/help.clj`, and `.gitignore`; it never overwrites existing files. It does not create an empty `spools/` directory; workspace-owned code normally uses a `:file` module. A workspace carrying legacy `libs.edn`/`libs.local.edn` fails init loudly with rename remediation (`spools.edn`/`spools.local.edn`, top-level `:libs` to `:spools`) rather than being migrated or ignored. Created config uses only `"configFormat":"alpha"` and does not persist source. Generated `spools.edn` seeds `millstrand.spools/batteries {:millstrand/source-root "spools/batteries"}`; the relative coordinate is resolved at runtime against the mill-resolved Millstrand source checkout and persists no absolute checkout path. Deleting that entry is the supported visible opt-out. The selected workspace's `.gitignore` ignores only the local overlays: `config.local.json`, `init.local.clj`, and `spools.local.edn`. Generated `init.clj` requires `millstrand.api.current.alpha` and `millstrand.api.runtime.alpha`, captures `(current/runtime)`, declares batteries as a normal `:spools`-guarded module, then activates the generated `me/help.clj` module with the same root guard after batteries. The adapter registers Batteries' builtin default help transform so fresh workspaces render `strand help` as text through the approved-coordinate path while `strand help --json` remains raw. Repo-world bootstrap (no `--workspace`) additionally ensures the repository-root agent guidance file carries a marker-guarded `## Millstrand / strand` section pointing new agents at `mill prime millstrand` and `strand --help`: it appends the section to whichever of `AGENTS.md`/`CLAUDE.md` exist (idempotent via the `<!-- mill:millstrand-prime -->` open marker with a matching `<!-- /mill:millstrand-prime -->` close marker bounding the block, append-only, never rewriting existing prose) and creates `AGENTS.md` when neither exists. Explicit `--workspace` bootstrap performs no guidance injection.
- **SPEC-002.C14b:** `mill init --stealth` is the explicit exception to C14a's repository guidance injection. It is valid only without
  `--workspace` and selects the canonical Git-root `.millstrand` or `.ms`. Before writing anything, it refuses tracked `.millstrand` or `.ms` paths and malformed
  mill-owned marker blocks. It bootstraps ordinary workspace files without editing shared `AGENTS.md` or `CLAUDE.md`, then maintains this
  exact block in `.git/info/exclude`: `# mill:millstrand-stealth`, `/.millstrand`, `/.ms`, `/CLAUDE.local.md`, `# /mill:millstrand-stealth`. It maintains the
  exact C14a guidance block in an untracked `CLAUDE.local.md`; a tracked `CLAUDE.local.md` is left untouched. An absent owned file is
  created with the exact block. A non-empty marker-free file keeps its bytes and gains a separating newline plus the block. Exact blocks,
  including their final newline, are unchanged; partial, duplicate, reordered, or edited blocks are semantic refusals. The existing `config_dir` and
  `config_file` success keys gain a typed `stealth` object with closed `git_exclude` (`path`, `status`), `claude_guidance` (`path`,
  `status`), and `codex_guidance` (`status`, `suggested_text`) children. File status values are `created`, `updated`, `unchanged`, and,
  for Claude guidance only, `skipped-tracked`; Codex status is `manual-required`. Go response structs validate this shape before emission.
  Semantic refusals use code `mill/init-stealth-refused` and exactly `path`, `target`, `state`, and `remediation` details. Target values are
  `tracked-millstrand`, `git-exclude`, and `claude-guidance`; state values are `tracked`, `start-only`, `end-only`, `duplicate-start`,
  `duplicate-end`, `reversed`, and `edited`. Ordinary `mill init` output remains unchanged.
- **SPEC-002.C15:** `mill` uses Cobra for its command tree and help text. The `strand` dispatcher owns its fixed flag set directly and must clearly describe the dispatcher contract in `--help`; it has no command tree to document.
- **SPEC-002.C15a (mill failure output):** A failed `mill` invocation prints exactly one error rendering (SPEC-002.C4b), then only the guidance its failure class earns. An unknown command adds a single pointer at `--help` for the command Cobra did resolve. A malformed invocation — a flag Cobra cannot parse, or an argument count a command rejects — adds that command's usage block. Both classes are recognised structurally, never by matching error text. A command that ran and failed adds neither: a flag list explains nothing about an unreachable weaver. `mill bin` failures stay the structured JSON envelope alone (SPEC-002.C54/C55) and gain no guidance. Neither does any failure under `MILLSTRAND_ERROR_FORMAT=json`: the envelope line is the whole of stderr, with no usage block and no `--help` pointer after it (SPEC-002.C4e).
- **SPEC-002.C16:** `mill weaver start` resolves the selected workspace and starts that workspace's Clojure weaver as a mill child process using mill-derived XDG state/data dirs and mill-resolved source, returning selected workspace JSON status without running the weaver in the foreground. `--name <name>` sets a non-empty friendly weaver name; when omitted, mill resolves the name from `config.local.json` `"name"`, then `config.json` `"name"`, then the selected workspace basename. `--ready-timeout <dur>` sets the startup wait budget as a positive Go duration; omitted uses 5m. If source resolution fails, startup fails with remediation naming the accepted sources. The weaver owns storage selection/preparation and loads selected workspace startup files in order: `init.clj`, then `init.local.clj`; missing files are skipped and present failing files fail startup loudly. Startup waiting allows for JVM boot plus trusted config work before reporting ready status. On timeout, mill terminates the still-starting weaver rather than leaving an orphan. Weaver stdout/stderr are captured to `weaver.log` in the weaver state dir — appended across restarts, never forwarded to mill's own log, and left in place by artifact cleanup so a failed boot stays post-mortem readable; startup failures carry the log path and its tail in the error, and weaver status JSON carries `log_path`.
- **SPEC-002.C17:** `mill weaver repl` verifies the selected workspace's weaver is running and attaches to its nREPL endpoint using mill-resolved source launch context. Mill does not proxy nREPL traffic. Any launched local process is a thin transport/UI attach client only; user forms evaluate in the weaver JVM.
- **SPEC-002.C17a:** `mill prime millstrand` prints harness-agnostic agent context to stdout and needs no running mill or weaver. It resolves the Millstrand source with SPEC-002.C3 precedence and prints exactly two newline-terminated labeled absolute paths: `Millstrand source: <resolved-source>` and `Millstrand reference: <resolved-source>/docs/reference.md`, with the reference path assembled for the host filesystem. It carries no independent orientation prose. A missing or non-regular reference file fails non-zero with its path, and an unresolvable source fails non-zero. Use `strand --help` for the CLI orientation that the Go dispatcher owns.
- **SPEC-002.C18:** `mill weaver repl --stdin` sends stdin Clojure forms to the selected running weaver nREPL for direct evaluation in the weaver JVM, prints one direct normal Clojure result per top-level form, and exits non-zero on read, eval, or transport errors. It does not impose a JSON or EDN response envelope.
- **SPEC-002.C19:** `mill weaver repl` and `mill weaver repl --stdin` are the public CLI paths for users and agents that need to run trusted spool-workspace Clojure code against a running weaver workspace.
- **SPEC-002.C20:** `mill weaver status` reports health, friendly name, selected config/data paths, weaver storage metadata (`database_kind`, `database_label`, `database_path` — canonical path for `sqlite-file`, explicitly `null` for `sqlite-memory`), the weaver log path (`log_path`), pid, weaver identity, socket endpoint, and nREPL endpoint when running, sourced from mill supervision state, runtime metadata, and a minimal socket health check. `mill weaver stop` stops only the selected workspace weaver child through mill supervision (signal-driven; SPEC-004.C26a) and cleans that workspace's runtime metadata/socket; non-supervised metadata-discovered weavers are signalled by pid with the same loud staleness checks.
- **SPEC-002.C20a:** `mill weaver list` returns a JSON array for editor/tooling discovery. Rows include `config_dir`, `state_dir`, `data_dir`, `database_kind`, `database_label`, `database_path`, `name`, `log_path`, and `state`; running rows also include `pid`, `weaver_id`, `socket_path`, `nrepl`, and `started_at`. The list includes supervised children and metadata-discovered weavers under the mill state root. Malformed metadata fails loudly instead of being silently repaired.
- **SPEC-002.C20b:** No public CLI command or flag selects weaver storage kind. CLI metadata/status validation compares `database_kind` and `database_label` for all storage kinds and `database_path` only for `sqlite-file`, failing loudly on malformed or inconsistent storage metadata. Mill supervises file-backed workspace weavers only and rejects other storage kinds in mill-managed weaver metadata.
- **SPEC-002.C21:** Runtime spool workspace, runtime transformation, lifecycle hook, attribute archive/migration, and registry mutation operations happen through selected workspace `init.clj`, blessed explicit-runtime `millstrand.api.*.alpha` namespaces, and trusted REPL workflows, not through dispatcher flags or mill commands. There are no package/spool/hook/batch activation commands, no public command archives attributes, and no public command migrates attribute storage.
- **SPEC-002.C48 (mill bin boundary):** `mill bin list`, `mill bin build <bin>`, and `mill bin run <bin> [args...]` are client-side mill verbs over the live weaver's read-only `bins` op. They are the exception to the old offline-only description of mill behavior: the weaver resolves declarations, while mill owns flag cutover, plan decoding, child-process behavior, descriptor cleanup, environment composition, and execution. Bin list and plan requests are non-interactive invokes (`is_tty=false`, `tty_col=null`); the later build or run child inherits the caller's terminal as specified below. `strand` gains no bin execution path and remains a pure dispatcher.
- **SPEC-002.C49 (bin list):** `mill bin list` relays the `bins list` result as one JSON object. The result contains the effective winning declarations after owner and override resolution. An empty `:bins` registry returns an empty `bins` collection. The command does not inspect the filesystem and does not start a process.
- **SPEC-002.C50 (bin run):** `mill bin run <bin> [args...]` requests `bins plan <bin>`, refuses a false `runnable` plan with the named bin outcome, then constructs argv from the resolved executable followed by every trailing argument unchanged. Flag parsing stops at `<bin>`; mill flags, including `--workspace`, precede it. Mill preserves the caller's cwd, closes every Millstrand-owned descriptor other than stdin/stdout/stderr, and calls `syscall.Exec`. A successful exec emits no result from mill. The bin inherits the caller's terminal directly, including its controlling session and foreground process group.
- **SPEC-002.C51 (bin build):** `mill bin build <bin>` requests the same plan and requires its optional `build` value. It starts the declared argv as a child with the plan's build cwd, leaves stdin/stdout/stderr attached to the caller, waits for exit, and emits the JSON build result. A missing recipe is `bin/no-build-recipe`; a process that cannot start is `bin/build-start-failed`; a started process with a non-zero exit is `bin/build-failed`. There are no completion stamps, locks, staleness checks, or toolchain installs. Re-running the declared recipe is the recovery path.
- **SPEC-002.C52 (typed bin plan):** Mill decodes the `bins plan` result as a typed object with `bin` (string), `runnable` (boolean or null), `exec` (object), and optional `build` (object). `exec` carries exactly one of `path` (canonical absolute string) or `command` (unchanged bare name), plus an `env` string-to-string overlay. `build`, when present, carries `argv` (non-empty string vector) and `cwd` (absolute string). Both keys in `exec`, neither key, malformed values, or an unexpected field type are client decode failures, not fallback cases.
- **SPEC-002.C53 (bin environment):** Mill composes the child environment from the caller's complete environment plus the plan's `exec.env` overlay. The overlay contains `MILLSTRAND_WORKSPACE`, set to the selected workspace path. It carries no run id, weaver id, or peer name. The plan does not echo the caller's cwd or environment. A wrapper reads `MILLSTRAND_WORKSPACE` when it needs to invoke ordinary `strand` ops against the selected world.
- **SPEC-002.C54 (bin outcomes):** The build success result is a JSON object with operation `bin build`, the bin name, the child exit code, and elapsed milliseconds. `bin run` reports no success envelope because mill has been replaced by the executable. Lookup, planning, relay, build, and exec failures remain structured non-zero CLI failures; the host cause and relevant path or argv are preserved where the outcome names them.
- **SPEC-002.C55 (bin failure outcomes):** `bin/unknown` means no active declaration has the name; `bin/anchor-unresolved` means a `:family` or `:root` anchor cannot resolve from the declaring file; `bin/not-built` means a declared build recipe has a false runnable predicate; `bin/not-runnable` means a buildless bin has a false predicate; `bin/no-build-recipe` means build was requested without a recipe; `bin/build-start-failed`, `bin/build-failed`, and `bin/exec-failed` describe the corresponding host process failures. A bare command has `runnable` null, so mill attempts it and reports an exec failure only if the host cannot start it.

## SPEC-002.P5 Removed surface and non-goals

- **SPEC-002.C40:** The builtin strand command tree is removed with no aliases (TEN-000@1): `init`, `add`, `update`, `show`, `supersede`, `burn`, `list`, `ready`, `graph subgraph`, `weave`, `query list|explain`, `pattern list|explain`, the `op <name>` prefix, and `weaver start|repl|stop|status` as strand subcommands. Everyday command behavior is batteries ops ([`spools/batteries.md`](../../spools/batteries.md)); bootstrap/lifecycle is mill. Client-side attribute-input flags (`--attr`, `--attr-file`, `--attr-stdin`, `--attributes-stdin`, `--edge`, `--state`, `--query`, `--param`) are op argv now — the dispatcher carries payload slots instead.
- **SPEC-002.C41:** No stream-in: requests stay one bounded envelope; bounded bulk input is a payload parsed and applied op-side in one transaction. Unbounded live ingestion belongs to spools inside the weaver, never a dispatcher flag.
- **SPEC-002.C42:** No hook bypass surface of any kind — permanent invariant.
- **SPEC-002.C43:** Historical per-command contracts (old SPEC-002.C5–C13c, C22–C25) are superseded; their behavior equivalences are recorded in `spools/batteries.md` and the archived op-only-cli feature folder.
