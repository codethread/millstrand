# Weaver Runtime

**Document ID:** `SPEC-004` **Status:** Implemented **Last Updated:** 2026-09-01 **Related RFCs:** [RFC-002 Task Query DSL](../rfcs/2026-06-24-task-query-dsl.md), [RFC-003 Fast JSON Socket CLI](../archive/26-06-25__go-cli-migration/rfcs/2026-06-25-fast-json-socket-cli.md), [RFC-004 Go CLI Migration](../archive/26-06-25__go-cli-migration/rfcs/2026-06-25-go-cli-migration.md) **Code:** `src/millstrand/core/weaver`, `src/millstrand/core/client.clj`, `src/millstrand/api/weaver/alpha.clj`, `cli/`

## SPEC-004.P1 Purpose

The weaver runtime is the long-lived local Clojure process that owns strand storage access, query execution, and runtime extension state for CLI and REPL clients.

## SPEC-004.P2 Runtime model

- **SPEC-004.C0a:** The alpha mill router runtime adds a local Go `mill` process as the known XDG entrypoint for routing/supervision. The mill owns process routing metadata only; the weaver remains the semantic runtime that owns storage, query execution, runtime registries, trusted config evaluation, hooks/events, and REPL semantics.
- **SPEC-004.C1:** A weaver owns the runtime subsystems specified below: storage, owner-partitioned registries, event dispatch, one generation basis and classloader, module refresh, spool state, one Clock, scheduling, and process custody.
- **SPEC-004.C1a:** A weaver runtime owns exactly one `millstrand.api.clock.alpha/Clock` for its
  lifetime. The Clock reads the current `java.time.Instant` and sleeps for a non-negative
  `java.time.Duration`; the production system Clock uses real wall time and blocking sleep. Core
  timer-driven subsystems and shipped spool polling use this Clock rather than calling wall-clock
  APIs directly; cosmetic failure and running-marker timestamps may still use wall time. Trusted
  callers obtain the same value with `millstrand.api.runtime.alpha/clock`, while `runtime/now` remains
  the data-first `Instant` read (SPEC-003.C17). The runtime-map slot and pump registry stay internal
  (SPEC-005.C5a). A manual Clock advances virtual time when slept. Before installation it runs no
  pumps; after `millstrand.test.alpha/set-clock!` installs it in one runtime, zero or positive sleeps
  run that runtime's pumps synchronously. `millstrand.test.alpha/advance!` requires a strictly positive
  Duration, advances an installed manual Clock, runs the same pumps, and returns the new Instant.
  Pump completion does not imply quiescence for unrelated event or subprocess work.
- **SPEC-004.C2:** A weaver exposes two local transports: nREPL for Clojure REPL/client workflows and a JSON Unix domain socket for the public Go CLI.
- **SPEC-004.C3:** Transports are local-only by default: nREPL binds to loopback, and the JSON CLI transport uses a Unix domain socket under the selected runtime state directory.
- **SPEC-004.C4:** A weaver workspace is selected by workspace. The CLI supplies this selected workspace after explicit `--workspace` handling or repository-canonical `.millstrand`/`.ms` discovery; Clojure entry points fail loudly when no selected workspace is provided. Without `--workspace`, linked worktrees for one supported non-bare Git repository converge on the same canonical repository `.millstrand`/`.ms` selected workspace. The unsupported legacy workspace name is rejected as an application marker.
- **SPEC-004.C5:** Runtime state for a selected workspace lives in the explicit selected state dir supplied at weaver startup, and weaver-owned data lives in the explicit selected data dir supplied at weaver startup. Mill derives those dirs from the canonical selected config identity, so linked worktrees that share the default workspace also share runtime/data/metadata identity.
- **SPEC-004.C6:** A selected workspace is a trusted config workspace only; config files load from that directory while runtime state and data may live in independent XDG dirs selected by mill. Mill owns Millstrand source checkout resolution for launching the weaver and any thin nREPL attach client used by `weaver repl`; the weaver receives explicit `--workspace`, `--state-dir`, `--data-dir`, and optional `--name` values and does not read source from `config.json`.
- **SPEC-004.C7:** The weaver owns storage selection. By default it uses `millstrand.sqlite` under the selected data dir. Public clients do not choose storage paths.
- **SPEC-004.C7a:** Weaver-owned SQLite access is configured for concurrent in-process writers from sockets, event handlers, and spool worker threads to wait briefly on write-lock contention rather than fail immediately. Mutating transactions acquire write intent at transaction start so lock waiting happens at a predictable boundary.
- **SPEC-004.C8:** A selected workspace may have at most one running weaver. Starting another weaver for the same selected workspace fails loudly unless stale socket/metadata can be proven dead and cleaned.
- **SPEC-004.C8a:** In one JVM, runtime existence is distinct from ambient publication. `millstrand.core.weaver.runtime/start!` publishes the new runtime as the process ambient runtime by default and fails loudly if another runtime is already published. With `:publish? false`, it starts an unpublished runtime; any number of unpublished runtimes may coexist when they use independent selected workspaces. `stop!` clears ambient publication only when the stopped runtime owns it.
- **SPEC-004.C8b:** `millstrand.api.current.alpha/runtime` resolves the current runtime in this order: thread-local runtime binding, published ambient runtime, then a loud failure. Startup and refresh config evaluation and built-in op registration bind the serving runtime so trusted config code using `current/runtime` works for unpublished runtimes.
- **SPEC-004.C9:** Multi-weaver use is explicit workspace selection: different selected workspaces create separate weaver/socket/metadata/data/init workspaces. Explicit `--workspace` is the intended isolation mechanism for Millstrand development, tests, and worktree-local experiments. Public request payloads do not carry cwd, repo metadata, storage paths, or source checkout paths as workspace identity.

## SPEC-004.P3 Runtime metadata and discovery

- **SPEC-004.C9a:** The mill router publishes its entrypoint under Millstrand's XDG state root: `$XDG_STATE_HOME/millstrand` or `~/.local/state/millstrand` when `XDG_STATE_HOME` is unset. Mill metadata lives at `mill.json`, and the mill JSON socket lives at `mill.sock`.
- **SPEC-004.C9b:** Mill derives per-workspace runtime directories under `<state-root>/weavers/<hash>`, where `<hash>` is a filesystem-safe hash of the canonical selected config identity.
- **SPEC-004.C10:** The JSON socket path is fixed within the selected state workspace as `weaver.sock`.
- **SPEC-004.C11:** Runtime metadata is published beside the fixed socket as `weaver.json` for Go clients and `weaver.edn` for Clojure clients.
- **SPEC-004.C12:** Runtime metadata records enough identity for clients to connect and verify intent: pid, weaver id, opaque `generation_id`, product version, protocol version, friendly name, selected workspace, selected state dir, selected data dir, storage kind and label plus weaver-owned database path (file storage only) for status/debugging, nREPL endpoint data, JSON socket path, and startup time. The Weaver reads its product version from the reserved Millstrand source root's `VERSION` file during startup and requires it to match the version supplied by its launching Mill; the value is independent of protocol version and the generation basis fingerprint. The friendly name defaults to the selected workspace basename unless launch supplied an explicit name or the selected workspace config declared one (SPEC-002.C2/C2a). Metadata does not record source as selected workspace identity; source is mill-owned launch context.
- **SPEC-004.C13:** Public Go CLI clients dial the local mill (SPEC-002.C1, SPEC-004.C9a); mill discovers the selected-workspace weaver by state workspace and forwards the request over the weaver socket, verifying weaver identity/protocol on that leg. Trusted Clojure clients discover the weaver by selected workspace/state workspace and verify weaver identity/protocol over the socket directly. Neither needs a database path to locate metadata, and neither sends or compares database path as a request identity field.
- **SPEC-004.C14:** Stale, missing, mismatched, malformed, or unreachable runtime metadata is an error; clients must fail loudly rather than silently opening SQLite directly. Product version is required: both Go and Clojure clients reject version-less metadata instead of admitting it as a compatible legacy generation, and a stamped Mill also rejects a Weaver product version different from its own. Clients discover only `weaver.*` artifacts and do not fall back to old `daemon.*` metadata. `mill weaver list` discovers supervised children and `weaver.json` files under the mill state root, returning running/stale rows for known selected workspaces and failing loudly on malformed metadata.

## SPEC-004.P3a Weaver storage model

- **SPEC-004.C91:** A weaver runtime owns exactly one storage handle for its lifetime. The handle carries the storage kind, a diagnostic label, an optional canonical filesystem path, a next.jdbc-compatible connectable, and optional close behavior. Startup normalizes storage into the handle before database initialization and metadata publication, then opens SQLite with WAL journaling, a non-zero memory map size, and an enlarged page cache for every world. Runtime stop closes runtime-owned spool-state resources with `:close-fn` after transports and event dispatch stop but before storage closes, then closes weaver-owned storage resources. Failed startup follows the same ordering for any spool state initialized before the failure: close runtime-owned spool-state resources before storage, suppressing close-hook failures onto the original startup exception so cleanup cannot mask the startup cause, then close storage on the error path.
- **SPEC-004.C91a:** Weaver storage initialization creates dedicated scheduler tables (SPEC-004.P10d) beside the strand graph. Scheduler rows are weaver runtime coordination state owned by the scheduler contract, not user graph rows; they never appear in strand `list`/`ready`/query/traversal/burn/update paths.
- **SPEC-004.C91b:** Storage initialization is schema-generation-aware; there is no implicit migration (TEN-000@1). It reads the database's schema generation — a monotonically increasing integer in SQLite's native `PRAGMA user_version` — before any DDL and classifies startup: a database stamped newer than the binary's generation is refused without modification (the binary is too old for the data); an older stamped generation is refused with a pointer to the maintained forward-migration path (C91d); an unstamped empty database is bootstrapped with the full schema, canonically validated, and stamped with the binary's generation; an unstamped non-empty database takes the adoption path (C91c); and a database at the binary's generation passes pre-DDL screening, receives the `IF NOT EXISTS` DDL (which back-fills declared-additive auxiliary objects only), and is then fully validated. Incompatible-generation errors report both the found and the expected generation, and refusals never write to the database, so opening a legacy or skewed database cannot leave a mixed partial schema behind.
- **SPEC-004.C91c:** A non-empty database with no stamp whose present objects pass pre-DDL screening against the generation-1 reference is adopted by stamping `user_version = 1` in place; no row data is touched, adoption is idempotent, and the stamp is written only after post-DDL full validation. The canonical validator compares Millstrand-owned tables and indexes against a freshly constructed reference schema: exact columns, order, declared types, nullability, defaults, primary keys, foreign keys, CHECK constraints, index columns and order, uniqueness, and partial-index predicates, rejecting extra columns on managed tables. A generation's **baseline** is its frozen reference schema; objects introduced additively within a generation sit outside the baseline until the next bump folds them in. Pre-DDL screening — applied to stamped-current and unstamped-adoption databases alike — requires every baseline object present and exact, permitting only additive-since-baseline objects to be absent, so a missing or malformed baseline object refuses initialization instead of being silently recreated by the DDL and then passing full validation.
- **SPEC-004.C91d:** Every schema-generation bump must ship maintained, ordered forward migrations from every released stamped generation. Each step updates schema, data, and `user_version` transactionally; a non-transactional step must define and test durable recovery. The outgoing reference schema is retained and additive objects join the new baseline. Generation 1 ships only the generation constant, gate, and stamp; the first real migration decides the code home and invocation surface.
- **SPEC-004.C92:** `:sqlite-file` is the default storage kind for normal weaver workspaces. It uses `millstrand.sqlite` in the selected data directory reported as `data_dir`; its canonical path is reported as `database_path`. Trusted runtime construction may supply another database file. The selected workspace holds config, and the selected state directory holds runtime artifacts; neither is the default database directory.
- **SPEC-004.C93:** `:sqlite-memory` is available only to trusted test/runtime construction. It uses real Xerial SQLite JDBC with a weaver-owned held `java.sql.Connection` running the same schema and SQL code as file storage; data is weaver-lifetime only, closing the connection destroys the database, and later use of closed storage fails loudly. One held connection serializes writes, so memory storage is test storage, not production-like pooled storage. The public CLI cannot select storage kind.
- **SPEC-004.C94:** Metadata reports storage identity explicitly. EDN metadata uses `:storage-kind`, `:storage-label`, and `:canonical-db-path`; JSON metadata and socket status use `database_kind`, `database_label`, and `database_path`. For file storage the label and path are both the canonical database path; for memory storage the label is a stable weaver-lifetime diagnostic string and the path is explicitly nil/null — never a fake filesystem path. Kind/label/path consistency is validated fail-loud both when metadata is published and when clients read it.
- **SPEC-004.C95:** `millstrand.api.runtime.alpha/spool-state` is the sole accessor for runtime-owned per-key spool state, initialized once with `init-fn` and reused for the runtime lifetime. Spool-state entries deliberately survive `refresh!` (unlike the owner partitions C46 replaces), so a spool whose state shape changed between deploys must not silently reuse a preserved value missing the new keys. The four-arg arity takes opts `{:version v :migrate-fn f}`: the declared `version` is stored as value metadata, and when a preserved value's stored version does not equal the currently declared `version`, the runtime deliberately reinits rather than reusing shape-mismatched state — running `init-fn` fresh after best-effort `:close-fn` release of the old value (preserving nothing), or, when `:migrate-fn` is supplied, handing the old value to `f` (which then owns the old value's resources) to produce the new one. Versioned state must support metadata. The three-arg arity is unversioned (version nil) and always reuses an existing value; consumers that store executors, schedulers, or other shape-sensitive resources declare a version and bump it whenever `init-fn`'s key set changes. The batteries read cap is runtime state set by trusted config through `millstrand.spools.batteries/set-read-limit!`; invalid cap values fail loudly. The opts map is validated at the call site — closed to `:version`/`:migrate-fn`, `:version` must be a non-nil integer/keyword/string, and `:migrate-fn` must be a function that requires a `:version` — so a misspelled key (`{:versoin 2}`) or malformed value fails loudly instead of silently degrading to the unversioned reuse path. When a preserved value mismatches the declared version, the reinit transition is serialized per runtime so `migrate-fn`/`init-fn` and the resources they build run at most once: concurrent accessors racing the same mismatch never each construct a replacement (a discarded loser would leak the executors/schedulers it built for the JVM lifetime), and a best-effort `:close-fn` failure during the release is warned rather than silently swallowed.
- **SPEC-004.C96:** `refresh!` never leaves a world with no ops. Built-in ops live under the system owner and are never cleared by refresh; a dependency failure or refused publication aborts before any owner partition changes.

## SPEC-004.P4 API boundary

- **SPEC-004.C15:** The `millstrand.api.*.alpha` namespaces are the semantic boundary used by trusted in-process code and fixed-form clients; their public functions take the target runtime as their first argument. Transport-specific eval strings, JSON envelopes, nREPL messages, and wire details are not the durable product API.
- **SPEC-004.C16:** Public domain namespaces own the trusted runtime surface. `millstrand.api.weaver.alpha` owns storage initialization and strand, relation, archive, named-query execution, and op-registry primitives. `millstrand.api.graph.alpha` owns named-query registration and introspection plus set-oriented graph reads and mutation. The `patterns`, `events`, and `hooks` namespaces own their runtime registries; `batch` owns transactional graph mutation payloads; `runtime` owns spool and module declarations, refresh and reload, and runtime status. Their detailed behavior is specified by the clauses for each subsystem below.

- **SPEC-004.C16a:** Attribute archive operations are trusted Clojure config/REPL surface only. `archive-attributes!` marks all attributes, or an explicit non-empty key set, archived for one strand. `unarchive-attributes!` reverses that state. The names are deliberately attribute-scoped: the bare `archive!` verb stays unspent so strand-level archival, if it ever ships, can accrete under the natural name. Both validate the strand id and requested keys before writing — input validation is owned by the storage layer against `::specs/attribute-key-set`, and results are checked against `::specs/attribute-archive-result` at the API seam — commit atomically, run no lifecycle hooks, enqueue no event, and return a map carrying `:strand-id`, `:keys`, `:archived?`, and `:changed`. Archiving a registered immutable key is rejected because it would hide write-once history; unarchiving one is legal and is the recovery path for rows archived before enforcement existed (the write-once contract is SPEC-001's). Archived keys remain visible to full point reads but are omitted from hot-tier reads: trusted in-process `list`, `ready`, and query execution, plus the CLI/agent lean projections layered on those reads. A later write to an archived key records fresh hot data for that key; untouched archived keys stay archived.

- **SPEC-004.C17:** Weaver API return values are Clojure data with JSON-bearing database columns normalized before transport-specific formatting. Strand rows use `state`; they do not expose removed lifecycle fields such as `active`, `inactive_at`, `status`, or `final_at`. Trusted in-process point reads (`show`, `strands-by-ids`, and `subgraph`) decode attributes to full-fidelity Clojure maps including archived values. Trusted in-process `list`, `ready`, and query execution are hot-tier reads: they decode full values for non-archived attributes only and are unbounded by default for REPL/config workflows. The lean tier is layered above hot-tier reads at the CLI/agent op boundary, and the batteries `list`/`ready` command surface may call the trusted lean projections with an explicit result cap. That cap is a CLI/wire guard: storage probes `limit + 1` rows before attribute assembly, reports the total on overflow, and never truncates successful results.

- **SPEC-004.C17a:** The lean-tier omission descriptor is the shared `::specs/omitted-attribute-descriptor` contract. The canonical trusted spool reader `attr-get` fails loudly when handed a value conforming to that spec where a raw value is expected; its `ex-info` ex-data is `{:key <attribute-key> :strand-id <strand-id> :recovery "show <strand-id>"}` so a misrouted lean-projected strand surfaces immediately with enough context to recover.
- **SPEC-004.C18:** Weaver API failures preserve domain error information well enough for clients to exit non-zero with useful messages.

## SPEC-004.P5 nREPL transport

- **SPEC-004.C19:** nREPL remains available for direct live weaver REPL sessions, Clojure/JVM process clients, editor tooling, and fixed-form API helpers.
- **SPEC-004.C20:** Fixed-form Clojure clients call only weaver API forms generated by trusted client code; user CLI input for public JSON operations is passed as data arguments, not interpolated as executable code. Direct live REPL sessions are trusted and may evaluate arbitrary forms inside the weaver JVM.
- **SPEC-004.C21:** nREPL is not the public fast CLI transport; it remains the rich Clojure-native surface for direct live weaver REPL sessions, REPL helpers, and fixed-form Clojure client/API calls. `millstrand.repl` helpers evaluated inside the weaver JVM may use the active runtime for human ergonomics; explicit client/test contexts route fixed API forms through connected client metadata. Direct `eval` and editor `load-file` operations run with the serving runtime ambiently bound and its generation classloader installed. Fixed-form client eval resolves the runtime by the connected server's nREPL port rather than by the process ambient runtime, so client calls against unpublished runtimes in a multi-runtime JVM route to the runtime that owns that nREPL server. The blessed `millstrand.api.*.alpha` domain namespaces take explicit runtime arguments and do not perform connected-client routing.

## SPEC-004.P6 JSON Unix socket transport

- **SPEC-004.C22:** The weaver exposes a local JSON Unix domain socket (`weaver.sock`) advertised in Go-readable runtime metadata (`weaver.json`). The public Go CLI does not dial it directly: CLI clients reach the local mill JSON socket (SPEC-004.C9a), and mill forwards the `invoke`/`status` frames to the selected weaver's socket (SPEC-002.C1). Trusted Clojure clients and peers dial the weaver socket directly (SPEC-004.C85/C88).
- **SPEC-004.C23:** JSON socket requests are one request per connection and include protocol version, request id, weaver id, operation name, operation arguments, and an empty options object reserved for future protocol use.
- **SPEC-004.C23a:** The JSON socket accept loop may serve multiple client connections concurrently. A long-running trusted operation on one connection must not starve unrelated status, stop, or graph requests on other connections.
- **SPEC-004.C23b:** `protocol_version` is the binary/JAR compatibility key for same-tree CLI/weaver skew. A release bumps it atomically in the Go client and JVM only for a genuine wire break where the peers can no longer exchange frames. Changing the exact request or response frame keys is such a break. Product-version and build-identity additions inside operation arguments or opaque, accretion-bound result bodies are not wire breaks and do not bump it.
- **SPEC-004.C24:** JSON socket responses include protocol version, request id, success flag, result on success, and a structured error envelope on failure. Error types distinguish domain, protocol, and transport failures. The type taxonomy and envelope shape are contract; concrete error `code` strings are contract only where a clause specifies them individually (`operation/deadline-exceeded` C26b, `query/not-found` C36b, `hook/failed` C84) — other code strings and human-readable message text may change (SPEC-005.C7).
- **SPEC-004.C25:** The JSON transport dispatches to weaver semantic operations rather than duplicating SQL or query logic in transport handlers.
- **SPEC-004.C26:** The socket operation set is `invoke` plus a minimal `status` health/identity operation. `invoke` carries the envelope `{name, argv, payloads, cwd, worktree_root, git_common_dir, workspace, timeout?, is_tty, tty_col, client{pid,version,build_id}}` as the operation arguments inside the existing request frame and dispatches to the op registry; envelope shape is validated (loudly) but argument validation belongs to ops via the blessed parser. The default `status` result contains liveness and identity, including the Weaver's product version. The internal status argument `{"include_registry_projection": true}` explicitly requests the complete deterministic registry projection used by replacement probing; every kind has exactly `effective`, `owners`, and `provenance`, executable values are redacted as `{callable: true, class: string}`, map keys are strings, sets are sorted arrays, and no function or runtime handle crosses the socket. The `:millstrand.registry-projection/registry` spec validates this shape before encoding. Client identity is socket-level diagnostic data: visible to payload hooks in `:request/args`, not threaded into op handler context. Storage initialization is a weaver startup responsibility, not a public JSON socket operation.
- **SPEC-004.C26a:** There is no socket `stop` operation. Weaver shutdown is signal-driven: SIGTERM/SIGINT run the clean stop path (transports down, storage closed, `weaver.edn`/`weaver.json`/`weaver.sock` removed), and mill supervision owns sending the signal.
- **SPEC-004.C26b:** Request deadlines apply to single-result responses: the invoked leaf's `:deadline-class` supplies the default (`:standard` = 10s, `:unbounded` = none); an envelope `timeout` (milliseconds) overrides it. On expiry the connection returns an `operation/deadline-exceeded` domain error and the handler future is cancelled with interruption — no orphan success frame follows a reported timeout (interruption is cooperative; a mutation already mid-commit is not rolled back). Stream-class ops run unbounded and are never server-deadline-bounded, including when an envelope timeout is present; cancellation is client disconnect, which aborts the emitting handler on its next write.
- **SPEC-004.C26c:** Responses self-describe as single or stream. A single result is the existing one-frame response. A stream-class op's response is a header frame (`stream: true` with frame identity), the handler's emitted values verbatim (one flushed NDJSON line each, via the `:op/emit!` context callback), and a terminator frame (`done: true` with success/result or error envelope). A hook rejection before the header yields a single error frame; a handler failure after the header yields an error terminator. One request per connection is retained; a streaming response holds its connection open without starving others (SPEC-004.C23a).
- **SPEC-004.C27:** Query registry mutation/authoring, pattern registry mutation, CLI operation registry mutation, event handler operations, and lifecycle hook operations have no socket operations; those remain REPL/trusted config workflows. Read-only registry introspection reaches the socket only through registered read ops (core `help`; batteries `query`/`pattern`; the opt-in workflow CLI's `workflow list`/`show` over the workflow definition registry).
- **SPEC-004.C28:** `status` is a minimal health/identity check: it validates the matched weaver over the socket and reports identity/health data for client verification and `mill weaver status` composition. Full status reporting is mill's concern (SPEC-002.C20); shutdown is signal-driven (SPEC-004.C26a).

## SPEC-004.P7 Configuration and user code

- **SPEC-004.C29:** Core weaver startup works without a user init file.
- **SPEC-004.C30:** The weaver loads selected workspace startup files in order: `init.clj`, then `init.local.clj`. Missing startup files are skipped. Load errors in present files fail startup loudly with file context and publish no ready metadata.
- **SPEC-004.C31:** Trusted init code runs after weaver memory/socket state exists and before runtime metadata is published, so it may initialize weaver-owned runtime state through startup helpers such as `millstrand.api.graph.alpha/register-query!` after capturing the runtime explicitly (for example via `millstrand.api.current.alpha/runtime`).
- **SPEC-004.C32:** Trusted config and extension code runs with weaver process authority. Sandboxing, SCI execution, untrusted plugin isolation, capability restriction, remote weaver access, authentication, multi-user authorization, and startup hooks for storage customization are outside this contract.

## SPEC-004.P8 Named query registry

- **SPEC-004.C33:** Named queries are data-first EDN DSL definitions stored in weaver memory, not executable user functions.
- **SPEC-004.C34:** Registry names are simple unqualified names; symbol and keyword forms of the same name resolve to one entry.
- **SPEC-004.C35:** Registry contents are not durable across weaver restarts. Users reload runtime query definitions through trusted startup config or REPL helpers.
- **SPEC-004.C36:** Missing named-query resolution fails loudly with a clear domain error.
- **SPEC-004.C36a:** Query metadata listing returns a vector of serializable entries ordered by canonical name. Each entry contains the canonical `:name`, declared `:params` (the allowlist from map query definitions; empty for vector definitions), and `:referenced-params` (parameter references discovered by walking the effective `:where` expression for `[:param kw]` forms, including relation positions in `[:edge/out ...]` / `[:edge/in ...]` predicates). Entries do not embed full definitions.
- **SPEC-004.C36b:** Query explanation returns one query's serializable caller guidance: the listing fields plus `:where` (effective where expression as a JSON-safe projection), `:definition` (normalized registered definition as a JSON-safe projection), `:where-form` / `:definition-form` (exact `pr-str` EDN strings for trusted users and docs), and a short `:summary` stating that invocation happens through `list --query` / `ready --query` with runtime params. Unknown names fail loudly with the existing `query/not-found` domain error including available names.
- **SPEC-004.C36c:** Query introspection reaches the socket only through the batteries `query` op (`strand query list|explain <name>`), which dispatches to the weaver API introspection helpers with the same trim/leading-colon name normalization as named-query application; blank names fail as domain errors at normalization.

## SPEC-004.P9 Runtime dependency and module model



- **SPEC-004.C37:** Runtime extensions are normal trusted Clojure spools/modules made available to the weaver through selected workspace startup (`init.clj` then `init.local.clj`) or live weaver REPL workflows.

- **SPEC-004.C39:** `millstrand.api.runtime.alpha` is the blessed explicit-runtime API for module declaration, refresh, planning, status, code reload, and Var resolution. A selected workspace contains required `deps.edn`, optional `deps.local.edn`, shared `init.clj`, optional `init.local.clj`, configuration, and workspace-relative module files.

- **SPEC-004.C42:** The basis boundary invokes `clojure.tools.deps/create-basis` with the tools.deps root source, `:user nil`, the parsed `<selected-workspace>/deps.edn` as the project source, and the parsed `<selected-workspace>/deps.local.edn` as the later extra source when that readable regular file exists. It does not read the global user source or an enclosing project's project source. `deps.edn` is required. An absent `deps.local.edn` contributes nothing. Relative paths in both sources resolve from the selected workspace under ordinary tools.deps rules.

- **SPEC-004.C43:** After source composition, the basis boundary selects `:millstrand/weaver` when declared and then `:millstrand/local` when declared. An absent alias is not selected and is not an error. tools.deps owns composition: project `:deps`, `:replace-deps`, `:paths`, and `:replace-paths` apply before the later extra source; the extra source's top-level `:deps` and `:paths` replace collisions from the project source; resolve and classpath args apply afterward. Within the same map-valued alias key, later local lib values win; path values concatenate distinctly in alias order. Across different keys, tools.deps precedence remains unchanged: `:replace-deps` wins over `:deps`, `:replace-paths` follows `:paths`, and `:override-deps` wins regardless of which selected alias supplied it. Millstrand performs no parallel merge or coordinate translation.

- **SPEC-004.C44:** Before `create-basis`, the boundary rejects `io.millstrand/millstrand` anywhere either workspace source could contribute it to the selected launch, including top-level dependency maps and the two selected alias maps. Mill then supplies exactly one paired `io.millstrand/millstrand` coordinate from its resolved source as reserved launch data. The reserved value participates after workspace sources and selected aliases and cannot be overridden. The loud failure is `reserved dependency io.millstrand/millstrand is supplied by Mill`; it includes the resolved source path and offending value.

- **SPEC-004.C44a:** The boundary reads and parses each present dependency file once into a tools.deps map, validates the required canonical file and reserved-coordinate rule, then passes those parsed values inward. Missing, unreadable, non-regular, non-map, or malformed `deps.edn` data fails with `:status :invalid-dependency-config`, `:stage :deps-read`, `:source-path`, `:message`, `:cause`, and `:coordinate nil`. Equivalent faults in a present local overlay use its resolved path. Resolution failure uses `:stage :deps-resolve`, preserves the original cause, and includes `:coordinate {:lib symbol :value edn-value}` plus the source path when tools.deps identifies one offending coordinate; otherwise `:coordinate nil` is the explicit unresolved-coordinate outcome. The boundary does not catch and continue, retry, use a default basis, or reparse trusted interior values.

- **SPEC-004.C45:** The immutable generation fingerprint is `sha256:<digest>`, where `<digest>` is 64 lowercase hexadecimal digits over the UTF-8 bytes of one canonical EDN value. The value is one semantic projection containing the ordered parsed `:project` and optional `:extra` source intent, the ordered selected aliases, the stable identity of the Mill-supplied reserved runtime, resolved library coordinates, and resolved non-path arg semantics. It excludes resolved source paths, Maven and Git cache locations, canonical local-root locations, classpath roots, and other derived absolute path values. Authored path and coordinate intent remains in the parsed sources. Copied or relocated workspaces with equivalent source intent and resolution therefore have the same fingerprint; a source, alias, coordinate, or non-path arg edit has a different fingerprint. Canonical EDN recursively orders every map entry and set member by the UTF-8 byte ordering of that item's canonical EDN representation, preserves sequential order, uses ordinary tagged-independent EDN scalar printing, and has no metadata or reader-eval forms. The encoder rejects values outside that closed EDN domain. It emits no whitespace beyond the delimiters and one ASCII space between adjacent collection items. This digest is identity, not a cache key or compatibility version. The running runtime stores the fingerprint once and never mutates it.

- **SPEC-004.C45a:** `:millstrand.core.specs/basis-fingerprint` owns the internal `sha256:<64 lowercase hexadecimal digits>` string and `:millstrand.api.runtime.alpha/basis-fingerprint` is its public alias. `:millstrand.core.specs/generation-basis` owns the parsed sources and their resolved paths, selected aliases, reserved coordinate, basis projection, fingerprint, and classloader identity retained by the runtime. The basis constructor consults both core specs before startup activation; `runtime/status` consults the public alias and `::status-result` before returning data. Their owning docstrings are the generation-basis constructor and `millstrand.api.runtime.alpha/status`; their contract-doc reference is SPEC-004.C45-C45a. Invalid constructed values fail startup loudly; trusted interior consumers do not reparse dependency files or invent fallback values.

- **SPEC-004.C46:** One Weaver generation has one classloader built from the completed tools.deps basis. All shared and personal libraries, Maven artifacts, Git roots, `:deps/root` roots, local roots, exclusions, paths, and classpath overrides use their ordinary tools.deps resolution in that classloader. Module evaluation, `resolve-var`, event handlers, scheduled handlers, lifecycle callables, and registry dispatch resolve through it. `resolve-var` retains public input `::resolvable-symbol` and return `(s/nilable var?)`; its function boundary consults both through its `s/fdef`, and its docstring cites this clause. `reload-code!` accepts a lib present in the running basis through public input spec `::root-lib` and returns `::reload-code-result`; its function boundary consults its `s/fdef` and validates the result before return. Unknown libs and non-source-backed reload targets fail loudly. Neither function reads dependency files, resolves coordinates, or changes the classpath.

- **SPEC-004.C47:** A module declaration contains its owner, exactly one of `:ns` or workspace-relative `:file`, and optional `:load :image`, `:after`, and `:required?`. Public `::module-opts` owns this closed input and `::module-declaration` owns the normalized result within `::module-result`; `module!` consults the input spec before collection and validates its result before return, and its docstring cites this clause. Dependency presence never activates code. Startup and refresh collect `init.clj` then `init.local.clj`; a later declaration of the same owner replaces the earlier declaration. Owner-complete authoring, candidate validation, atomic publication, lifecycle reconciliation, omission, source/image behavior, and retained declaration records continue under their existing contracts.

- **SPEC-004.C48:** `runtime/refresh!` parses and resolves one candidate generation basis through SPEC-004.C42–C45 before evaluating either startup file or any module source. It compares the candidate fingerprint with the immutable running fingerprint. Equality permits the existing configuration/module refresh against the running classloader. A valid difference returns `{:status :restart-required :reason :dependency-basis-changed :basis {:running-fingerprint running :candidate-fingerprint candidate}}`; it publishes no registry, declaration record, module, lifecycle, resource, startup, or configuration change. Refresh never installs the candidate classpath. There is no fallback comparison, retry, partial activation, or speculative recovery.

- **SPEC-004.C49:** A failed candidate read returns `{:status :invalid-dependency-config :stage :deps-read :source-path path :message string :cause string :coordinate nil}`. A failed candidate resolution has the same status and uses `:stage :deps-resolve`; `:coordinate` is either `{:lib symbol :value edn-value}` with the resolved source path that supplied it, or nil when the resolver cannot isolate one coordinate. The original parser or resolver cause is required and non-blank. Both outcomes leave every running value and pending activation edit untouched. `:millstrand.core.specs/dependency-diagnostic` owns the internal closed shape and `:millstrand.api.runtime.alpha/dependency-diagnostic` is its public alias included by public `::refresh-result`; public `::basis-change` owns the closed `:basis` pair in the restart-required alternative. `runtime/refresh!` validates its result against `::refresh-result` before return. Its docstring owns the public Clojure promise and cites SPEC-004.C48–C49. Missing paths or causes, unknown stages, malformed coordinates, and contradictory status/stage data fail loudly.

- **SPEC-004.C50:** `plan` previews configuration and module publication only after the candidate basis passes SPEC-004.C48; on a changed basis it returns the same validated restart-required result and stages no activation. `status` reports modules, resources, loaded namespaces, `:basis-fingerprint`, and `:last-refresh`. Public `::plan-result` owns the plan shape and public `::status-result` owns the status shape. `plan` and `status` validate those specs before returning. Their docstrings cite this clause. Refresh and module results use `::refresh-result` and `::module-result`.

- **SPEC-004.C94a:** Weaver generation identity, restart records, fresh-generation probe ordering, admission, one-send delivery, process custody, owner reconciliation, interruption outcomes, scope, and coverage remain exactly governed by `SPEC-004.C113-C123`. The fresh probe and replacement each build one independent generation basis and classloader through SPEC-004.C42–C46. A dependency failure is visible at `deps-read` or `deps-resolve`; it does not trigger a retry or fallback basis. A failed probe retains and continues serving the admitted old generation. After cutover, a failed replacement remains failed and never readmits the old generation. Custodied work and all retained continuity cross a successful dependency-driven replacement unchanged.

## SPEC-004.P10 Runtime transformation primitives

- **SPEC-004.C51:** Millstrand ships blessed source-visible `millstrand.api.graph.alpha` and `millstrand.api.batch.alpha` namespaces for trusted runtime transformation workflows. They are built-in namespaces, not user/community spools.
- **SPEC-004.C52:** `query-ids` returns a vector of strand ids for an ad hoc query definition or registered query name, ordered by the same stable strand ordering as `list` query results.
- **SPEC-004.C53:** `burn-by-id` and `burn-by-ids` physically delete strands and incident edges. `burn-by-ids` preserves first-occurrence input order with duplicates collapsed in its `:burned` result, returns `{:burned [] :count 0}` for empty input, and fails loudly if any requested id is missing.
- **SPEC-004.C53a:** `strands-by-ids` accepts a collection of strand ids, collapses duplicate ids by first occurrence, returns normalized strand rows in that first-occurrence input order, returns `[]` for empty input, and fails loudly if any requested id is missing.
- **SPEC-004.C54:** `ancestor-root-ids` traverses upward over one declared acyclic relation, defaulting to `parent-of`, where parent `from_strand_id` points to child `to_strand_id`. Seed ids are depth-zero candidates. With `:where`, it returns topmost matching ancestors on every path; without `:where`, it returns graph roots with no parent in the selected relation. Results are deduplicated and stable-sorted by id. Empty seed input returns `[]`; any missing seed id fails loudly. Traversal over undeclared annotation relations fails loudly.
- **SPEC-004.C55:** `subgraph` expands downward over one declared acyclic relation, defaulting to `parent-of`, from root ids and returns `{:root-ids [...] :strands [...] :edges [...]}`. The JSON socket accepts `{"root_ids":[...],"type":"relation"}` with `type` optional, and transports the same normalized graph shape as JSON. `:root-ids` preserves first-occurrence input order with duplicates collapsed. `:strands` contains normalized rows for roots and descendants, ordered by stable strand id. `:edges` contains only internal selected-relation edges connecting included strands, ordered by `from_strand_id`, `to_strand_id`, then edge type. Empty root input returns `{:root-ids [] :strands [] :edges []}`; any missing root id fails loudly. Traversal over undeclared annotation relations fails loudly.
- **SPEC-004.C55a:** `incoming-edges` and `outgoing-edges` resolve one strand-set's direct adjacency for a given edge type without graph traversal: `incoming-edges` returns edges whose `to_strand_id` is one of the ids (a strand's parents/annotators, indexed on `(to_strand_id, edge_type)`), and `outgoing-edges` returns edges whose `from_strand_id` is one of the ids (a strand's children, indexed on the `from_strand_id` primary-key prefix). Both take any valid edge type (annotation relations included — no acyclicity requirement) and return normalized `{:from_strand_id :to_strand_id :edge_type :attributes}` rows ordered by the queried side then the other. An empty id set returns `[]` without querying. Adjacency is deliberately lenient — unlike `subgraph`, `ancestor-root-ids`, and `strands-by-ids`, which fail loudly on a missing seed id, these edge-projection primitives treat an id absent from `strands` as indistinguishable from one with no matching edges (both contribute no rows), so callers needing a missing-id error validate at their own boundary.
- **SPEC-004.C56–C59:** Retired. The weaver-memory view registry these clauses specified was cut before the v1 stamp with zero first-party consumers; registered read-class CLI operations and named queries are the read surface. The IDs are not reused.
- **SPEC-004.C59a:** Batch graph mutation uses the weaver operation name `:apply-batch`. It accepts the trusted batch payload contract and returns normalized Clojure data without requiring JSON socket exposure.
- **SPEC-004.C59b:** Pattern-created batches through `weave` and trusted transactional graph batch mutation through `apply-batch` are two doors into one transactional batch engine at different trust tiers: `weave` is the named, spec-checked, create-only CLI-safe door; raw batch remains trusted Clojure because it can create, update, burn, and upsert edges.
- **SPEC-004.C60:** Pattern registry entries are named by simple unqualified names and point to an optional non-blank doc string, fully qualified Clojure function symbol, and input spec name resolvable in the weaver JVM. Registration input and entries conform to the owning `millstrand.core.specs` contracts. Duplicate registration replaces the prior entry for reload workflows.
- **SPEC-004.C61:** Pattern invocation validates input against the registered spec before calling user code, invokes the function with `{:input input}`, requires a batch strand vector return value, and delegates persistence through the weaver API for id generation, ref resolution, edge insertion, cycle checks, transactionality, and lifecycle hook policy.
- **SPEC-004.C62:** Pattern explanation returns serializable guidance containing the pattern name, optional doc string, function symbol string, input spec string, printable spec form, and expanded schema details when available. This is caller guidance; invocation-time spec validation remains authoritative.
- **SPEC-004.C63:** Pattern registry contents are runtime state and are not durable across restarts. Refresh replaces each selected owner's complete partition and removes a full-graph owner by omission.
- **SPEC-004.C63a:** CLI operation registry entries are named by simple unqualified names and carry a fully qualified Clojure handler function symbol plus an op metadata map: `:doc`, `:arg-spec` (blessed parser spec), `:returns` (optional shared return-shape declaration), and `:stream?` (default false); unknown metadata keys fail loudly. Every op authors `:hook-class` and `:deadline-class` only on its arg-spec leaves. Registration opts carrying either key fail loudly. Registration and replacement validate `:returns` through `millstrand.api.return-shape.alpha` and retain it in the registry entry. The registry records `:provenance` (the registering namespace, derived from the handler symbol) itself; caller-supplied provenance fails loudly. `register-op!` on an existing name fails loudly naming both registrants; deliberate override is explicit `replace-op!`, which requires the name to exist. Module publication replaces selected owner partitions atomically, so content-identical refreshes do not collide.
- **SPEC-004.C63b:** CLI operation invocation resolves the registered function symbol and calls it with one context map containing `:op/name`, raw string vector `:op/argv`, `:op/runtime`, `:op/runtime-metadata`, `:op/payloads` (default `{}`), and any envelope-supplied `:op/cwd`/`:op/worktree-root`/`:op/git-common-dir`/`:op/timeout`; stream-class invocations additionally receive `:op/emit!`. The blessed parser (`millstrand.api.cli.alpha`) runs first for every op — resolving whole-value payload references and validating argv — and supplies the parsed map as `:op/args`; parse failures are loud domain errors and the handler is not called. Declared returns are registration and discovery metadata: ordinary invocation does not check or transform the handler result, emitted stream items, terminal stream result, or socket encoding. The return value is transported as JSON-compatible data to `strand` callers, with one dispatch-owned amendment: when a declared arg-spec selects a subcommand and the handler returns a map, dispatch sets `:operation` to `"<op-name> <full-subcommand-path>"`, joining the parsed path vector with spaces. A handler-supplied `:operation` equal to the derived label is preserved; a different value, including explicit nil, fails loudly with expected and actual labels. Non-map results, thrown failures, and the dispatch-level help alias keep their unamended behavior. A blocking leaf declares `:deadline-class :unbounded`; sibling leaves retain their own classes.
- **SPEC-004.C63c:** The weaver installs built-in `help`, `about`, and `prime` operations under the system owner before module publication. `help` is a registry projection: no argv lists compact entries; one op name returns full parser and return-shape detail. Built-ins are replaceable only through explicit override intent, and removing a higher owner restores the system entry.
- **SPEC-004.C63d:** One canonical entry validator, owned by the op-entry module and shared with `register-op!`, validates every entry before it becomes effective: direct registration and module publication at generation reconcile. It runs the recursive arg-spec structural and class checks, return-tree validation, and glossary-reference checks after that generation's glossary contributions merge. The core registry's storage-side entry spec stays thin; hand-assembled contribution paths conform through the canonical validator and never recreate a class default.
- **SPEC-004.C63e:** Ops whose arg-spec declares `:subcommands` carry a help invocation alias: when the invocation's argv is exactly one token equal to `help`, `-h`, or `--help` and the envelope carries no payloads, the invocation returns the op's help detail projection (identical to `help <op>`, SPEC-004.C63c) as a normal successful single result. The alias resolves **before lifecycle hook gating** — a help-alias invocation is a read-class registry projection, so the target op's mutating-class hooks do not fire — and the handler is never called. Any other argv shape (extra tokens, attached payloads, the token in a non-sole position) is not an alias and flows through normal parsing and its loud errors; flat arg-spec ops never trigger the alias. `help`/`-h`/`--help` are reserved subcommand names (SPEC-003.C65), so the alias shadows nothing. **Superseded by SPEC-004.C108:** the sole-token `<op> help|-h|--help` alias is retired in favor of the trailing-`--help` flag rewrite across all op shapes, and the bare-word `<op> help` form now fails with a loud redirect (SPEC-002.C46).
- **SPEC-004.C63f (core bins registry and read protocol):** Core declares `:bins` as the sixth owner-partitioned registry kind beside `:ops`, `:queries`, `:patterns`, `:hooks`, and `:events`. Its permissive kernel entry spec is `:millstrand.core.weaver.core-registry/bin-entry`; the authoring constructor validates the closed declaration grammar through `:millstrand.core.contribution/bin-options` and `:millstrand.core.contribution/bin-entry`. The kind has the same complete owner-partition, collision, override, refresh, and omission semantics as the other core kinds. It has no candidate validator and performs no filesystem check during publication.
- **SPEC-004.C63g (bin paths):** A bin executable declaration is a non-blank string or a retained `[:family path]`/`[:root path]` anchor. `bins plan` resolves an anchor from the declaring source's unique tools.deps basis source root: `:family` from that library's canonical `:deps/root`, and `:root` from the matched canonical source path. An absent or ambiguous source or library root fails loudly as `bin/anchor-unresolved`.
- **SPEC-004.C63h (bins read operations):** Core registers the read-only `bins` op with `list` and `plan <name>` leaves. `bins list` returns the effective winning declarations and an empty collection when no active module declares a bin. `bins plan` resolves one declaration without opening a process or retaining a descriptor. Both leaves use the `:read` hook class and the standard deadline class. The list handler validates its result against `:millstrand.core.weaver.bins/list-result`; the plan handler validates its result against `:millstrand.core.weaver.bins/plan-result`. Those named specs are the consulted result contracts, not user-facing authoring forms.
- **SPEC-004.C63i (bin result shapes):** A list result carries operation `bins list` and a `bins` vector of declaration projections. Each projection carries the flat name, `spool`, doc, executable spelling, and optional build argv. A plan result carries operation `bins plan`, the requested bin name, `runnable` as boolean or null, `exec` with exactly one `path` or `command` plus its string-to-string `env` overlay, and an optional `build` map with non-empty string `argv` and absolute `cwd`. A path spelling is canonical absolute; a bare command remains unchanged and has `runnable` null. The selected workspace is the `MILLSTRAND_WORKSPACE` value in the overlay. The result shapes accrete under these keys; unknown fields are tolerated by consumers according to SPEC-002.C4a.

## SPEC-004.P10a Event helpers

- **SPEC-004.C64:** Millstrand ships `millstrand.api.events.alpha` as a blessed source-visible explicit-runtime namespace for trusted config and live weaver REPL workflows. It exposes handler registration, unregistration, registry introspection, and recent failure introspection. Event submission stays internal to mutation operations (SPEC-004.C73), and the blocking event-lane quiescence await ships in `millstrand.test.alpha` (SPEC-004.C74b).
- **SPEC-004.C65:** Event handler registration uses a stable key, a non-empty set of event type keywords, and a fully qualified function symbol resolvable in the weaver JVM through the generation classloader. Duplicate keys replace prior entries for reload workflows.
- **SPEC-004.C66:** Event registry introspection returns data-first entries containing handler keys, subscribed event type sets, handler function symbols, and metadata. It does not expose function values or worker internals.
- **SPEC-004.C67:** Event handler failures are recorded in bounded weaver-lifetime introspection state. Handler exceptions do not fail the already-committed mutation that emitted the event.
- **SPEC-004.C68:** Event helper operations route directly inside the weaver JVM with an explicit runtime argument; connected-client workflows use trusted `millstrand.core.client` calls instead. They are not public JSON socket operations.
- **SPEC-004.C69:** Event registry contents are runtime state, not durable storage, and are reinstalled by trusted startup config, activated spools, or live in-weaver REPL forms after weaver restart.
- **SPEC-004.C70:** Refresh does not globally stop the event lane. It re-reads the selected workspace startup files (`init.clj`, then `init.local.clj`), stages every owner contribution, and atomically replaces each affected owner's partition of the event-handler, CLI-operation, and other core registries while preserving queued events, recent handler failures, and unrelated owner partitions. An event dispatch, hook invocation, or op invocation already in progress finishes against the effective entry it snapshotted at dispatch start; later dispatch observes the replacement. Built-in CLI operations live under the system owner and survive refresh unless an explicit higher-layer override shadows them (SPEC-004.C63c). Refresh does not unload Clojure namespaces or remove already-loaded vars; a removed owner's contribution is retracted from the effective registries even though its vars remain loaded (SPEC-004.C46a).
- **SPEC-004.C71:** Events are Clojure maps with at least `:event/type`, `:event/id`, `:event/at`, and `:event/source`. Strand mutation events currently include `:strand/added`, `:strand/updated`, `:strand/superseded`, and `:strand/burned`.
- **SPEC-004.C72:** Add events include `:strand/id` and the normalized created `:strand`. Update events include `:strand/id`, submitted `:strand/patch` including any `:edges`, normalized `:strand/before`, and normalized `:strand/after`. Supersession events include `:strand/id`, `:strand/old-id`, `:strand/replacement-id`, normalized old-strand `:strand/before` and `:strand/after` rows, `:supersession/supersedes-edge`, and `:supersession/rewired-dependencies`. Burn events include `:strand/requested-ids`, `:strand/burned-ids`, and normalized pre-delete `:strand/before` rows.
- **SPEC-004.C73:** Events are emitted by Millstrand mutation operations after the database mutation succeeds, not by SQLite triggers or table watchers. Edge writes performed through `update` are represented by the same `:strand/updated` event in the MVP. Successful batch graph mutation emits `:batch/applied` first with final refs, created rows, updated before/after rows, burned ids/before rows, and edge outcomes. It then emits compatibility fanout in deterministic order: created strand events in result order, updated strand events in result order, and one aggregate `:strand/burned` event when any strands are burned. Compatibility fanout events include only a shared `:batch/id` for correlation; edge-only batch effects are represented by `:batch/applied` only.
- **SPEC-004.C74:** Event dispatch is asynchronous through a single sequential worker with a bounded queue. Enqueueing fails loudly when the queue is full. Recent handler failures are bounded to the latest 100 entries and include handler key, function symbol, event id/type, exception message, and time.
- **SPEC-004.C74a:** [`millhouse.spools.chime`](https://codethread.github.io/millhouse.spool/) declares one module-scoped `defresource` that owns its event handler, mutation barrier, and visible rule view as one atomic live boundary. Open and close hold the shared rule-view monitor; a failed open compensates to the inactive boundary, while a failed close restores the active boundary so the retained resource can be retried. Splitting this cluster into independent effects is invalid. The handler's runtime behavior and deduplication semantics remain owned by the external Chime spool contract.
- **SPEC-004.C74b:** `millstrand.test.alpha/await-quiescent!` `[runtime]` / `[runtime opts]` blocks until the single sequential event worker (SPEC-004.C74) has settled — the bounded queue is empty and no handler dispatch is in flight — then returns the runtime; on timeout it throws an `ex-info` (TEN-003), with a self-contained default budget of 10,000 ms overridable via `:timeout-ms`; repository tests that use `MILLSTRAND_TEST_AWAIT_SCALE` pass their scaled budget explicitly. "Idle" is an atomic dispatch-in-progress flag the worker raises *before* it claims an event and lowers after its handlers return, not a bare queue-empty check: because the worker claims an event before it could flip any flag, a naive queue-empty test could report settled while a just-claimed dispatch is still running. This is a lane-only test primitive — it settles the shared event lane and observes no off-lane completion a handler may have started (the shell executor's `:shell` subprocess on a private worker pool, chime's per-dispatch notifier daemon threads, a subagent-executor gate's agent run reaching a terminal state), which keep their own completion signal layered on top and is never smuggled into `await-quiescent!`. No bare `quiescent?` predicate is exposed, because the useful operation is the await and a predicate invites the caller-rolled sleep loop this seam replaces.

## SPEC-004.P10b Lifecycle hooks

- **SPEC-004.C75:** Millstrand ships `millstrand.api.hooks.alpha` as a blessed source-visible explicit-runtime namespace for trusted config, activated spools, in-weaver code, and live weaver REPL workflows. Lifecycle hooks are synchronous weaver-side policy gates, separate from asynchronous post-commit events.
- **SPEC-004.C76:** Hook registry entries contain a stable key, a non-empty set of hook type keywords, a fully qualified function symbol resolved through the generation classloader, an integer `:order` defaulting to `0`, and data-first metadata. Duplicate keys replace prior entries. Introspection returns entries in deterministic execution order, sorted by `:order` then key `pr-str`, and never exposes callable values. Entries are pure data carrying the symbol, never a captured callable: every hook — direct-registered or module-published — binds its callable at the hook's `:hook/dispatch-start` binding moment by resolving the symbol through the generation classloader, so a reload's fresh definition is the one that runs. Direct `register-hook!` additionally validates the symbol resolvable at registration; a symbol unresolvable at dispatch fails the gated operation through the standard `hook/failed` wrapper (SPEC-004.C84).
- **SPEC-004.C76a:** Hook registration input, entries, provenance, and public registry reader outputs conform to the owning `millstrand.core.specs` contracts. Public registry readers validate their returned data before exposing it to callers.
- **SPEC-004.C77:** Refresh replaces each hook owner's complete partition of the lifecycle-hook registry from the re-read selected workspace startup files (`init.clj`, then `init.local.clj`), leaving unrelated owners' hooks in place; hook registrations are runtime state and are not persisted in SQLite.
- **SPEC-004.C78:** Validation hooks receive exactly one context map. Their return values are ignored; returning normally approves and throwing rejects. Transform hooks are explicit families and must return `{:hook/value replacement}`. Invalid transform return shapes or replacement values fail loudly.
- **SPEC-004.C79:** `:attributes/normalize` transform hooks thread JSON-compatible strand attribute maps before candidate validation for add, update patches, transactional batch created/updated strand entries, and pattern-produced create-only strand entries. They do not normalize edge attributes. Context includes at least `:hook/type`, `:hook/value`, `:request/source`, `:request/operation`, and `:mutation/operation`, plus strand-specific keys when known such as `:strand/id`, `:strand/ref`, `:strand/before`, `:strand/patch`, `:batch/ref`, and `:pattern/name`.
- **SPEC-004.C80:** `:payload/received` hooks gate socket `invoke` by the invoked leaf's `:hook-class`: `:mutating` leaves run them and `:read` leaves skip them. The gate walks argv through the arg-spec to the leaf before hooks run. Missing or unknown tokens at any depth fail loudly before hooks with the canonical SPEC-003.C65 context; unknown ops do likewise. Flat arg-spec ops gate on their own mandatory class. Hooks run after JSON decode, protocol validation, identity verification, envelope-shape validation, and op resolution, but before semantic dispatch. They may reject but not transform. Context includes at least `:hook/type`, `:request/source :json-socket`, `:request/operation :invoke`, `:request/id`, `:request/args`, `:request/options`, and `:op/name`.
- **SPEC-004.C81:** Pre-commit mutation hook families are `:strand/add-before-commit`, `:strand/update-before-commit`, `:strand/supersede-before-commit`, `:strand/burn-before-commit`, and `:batch/apply-before-commit`. They run synchronously before durable mutation commit where throwing aborts the mutation. Hook-rejected mutations commit no partial graph change and enqueue no mutation events. Context always includes `:hook/type`, `:request/source`, `:request/operation`, and `:mutation/operation`. Add hooks receive candidate created strand data with no before row. Update hooks receive strand id, patch, normalized before row, normalized after candidate row, and candidate edge operations requested by the update patch. Supersession hooks receive old id, replacement id, old before/after candidate rows, supersedes edge candidate, and dependency rewiring candidate data. Burn hooks receive requested ids and normalized before rows.
- **SPEC-004.C82:** Batch hooks use one common context schema for graph batch and pattern-created batch entry points: `:batch/source`, `:batch/payload`, `:batch/refs`, `:batch/created`, `:batch/updated`, `:batch/burned`, and `:batch/edge-ops`; source-specific empty entries are present as empty vectors or maps. For transactional graph batch mutation, `:batch/source` is `:apply`, `:batch/payload` is the submitted payload, and the remaining batch keys describe final refs, created candidates, updated before/after candidates, burned before rows, and candidate edge operations. For pattern-created batches, `:batch/source` is `:weave`, `:batch/payload` is the pattern-produced create-only batch in normalized batch shape, `:batch/updated` and `:batch/burned` are empty vectors, and context includes `:request/operation :weave`, `:pattern/name`, and `:pattern/input`; pattern-created batches pass through batch policy once.
- **SPEC-004.C83:** Successful hook-approved mutations preserve existing post-commit event behavior. Event handler exceptions still do not fail an already committed mutation. Trusted code that bypasses `millstrand.api.weaver.alpha` and calls lower-level persistence namespaces directly opts out of the blessed hook contract.
- **SPEC-004.C84:** Hook invocation failures propagate to callers as `ex-info` with top-level code `hook/failed`, including hook type, key, function symbol, original exception message/class, original `ex-info` data when present, and original `:code` as `:hook/cause-code` when present. JSON socket failures use the domain error envelope with code `hook/failed` and structured details.

## SPEC-004.P10c Local weaver peering

- **SPEC-004.C85:** Millstrand ships `millstrand.api.peers.alpha` as a blessed source-visible client-side namespace for trusted config, activated spools, and live weaver REPL workflows. It is loaded from the mill-resolved source checkout and is not a public JSON socket operation family; all of its helpers read published runtime metadata and speak to peer sockets from the calling process, so they behave identically inside the live weaver JVM and in connected client workflows.
- **SPEC-004.C86:** `peers` enumerates sibling weavers by reading `weaver.edn` metadata files (the Clojure-client artifact, SPEC-004.C11) under the mill state root (SPEC-004.C9a/C9b) and returns data-first rows including friendly name, selected workspace, weaver id, protocol version, socket path, state dir, and a running/stale determination. Present malformed metadata fails loudly per SPEC-004.C14; stale rows are reported as stale and are never callable peers.
- **SPEC-004.C87:** `call!` resolves a non-row `peerish` argument to exactly one running peer by logical friendly name or by explicitly path-like selected-workspace input (contains `/`, or starts with `~`); bare tokens always resolve as logical names, so a local directory named like a peer never shadows the name. A name matching more than one running weaver fails loudly listing every candidate with its workspace path; unknown or stale matches fail loudly. There is no auto-start: peer lifecycle belongs to the caller.
- **SPEC-004.C88:** `call!` invokes a named op on a resolved peer via the `invoke` envelope (or the minimal `status` operation) over the existing protocol: one request per connection with protocol-version and weaver-identity verification (SPEC-004.C13/C14/C23/C24). There is no client-side operation allowlist; rejection is receiving-side — unknown-op domain errors and the peer's `:payload/received` hooks remain the policy gate. Peering adds no socket operations or protocol fields; the receiving weaver cannot distinguish a peer from any other local client. `call!` supports single-result responses; a peer answering with a stream header fails loudly (`:peer/stream-unsupported`) without consuming the stream. Malformed `args` — a non-map, non-string `argv` entries, or non-map `payloads` — fail loudly client-side (`:peer/invalid-args`) before any socket work. Peer domain errors surface as structured client errors carrying peer identity and the peer's error envelope. If replacement closes the peer connection after its first socket write, `call!` returns structured `weaver/restarted` only when the request was causally admitted before that transition and the valid durable restart record names the selected previous weaver and generation. A malformed present restart record fails loudly at the boundary; absent or mismatched restart evidence remains ordinary transport failure. `call!` never replays the request; a caller may reconnect and explicitly reissue only a read whose owner contract says that reissue is safe. A request interrupted before its first write is a transport failure and may be retried only by that caller's stated policy.
- **SPEC-004.C89:** Provenance for peer-initiated mutations is convention, not enforcement: peer callers identify themselves through existing freeform actor fields (for example workflow `complete!` `:by "weaver:<name>"`). The engine records nothing about caller identity beyond what operations already accept.
- **SPEC-004.C90:** Peering is same-machine, same-user only; SPEC-004.C32's exclusion of remote weaver access, authentication, and multi-user authorization is unchanged. Inter-weaver agreement is userland: the op registry (SPEC-004.C63a-c) is the contract surface, and each caller and provider owns its versioning, introspection, and deprecation conventions rather than the engine.

## SPEC-004.P10d Weaver scheduler

The weaver owns one scheduler subsystem for proactive durable wakeups: a substrate for the no-poller case, not a replacement for pull-based `wake-at` strand attributes plus named queries. It stores wake rows in dedicated SQLite tables, arms the next due wake inside runtime-owned state, and dispatches due handlers through the same serialized async mutation lane used by post-commit events (RFC-009). The blessed trusted-Clojure surface is `millstrand.api.scheduler.alpha` (SPEC-003.P4a).

- **SPEC-004.C97:** Scheduler state is runtime-owned, not module-level: it is acquired through `millstrand.api.runtime.alpha/spool-state` (SPEC-004.C95) with a declared version and a `:close-fn`, and it must not introduce a parallel module-level atom or bespoke reload registry. If the scheduler state shape changes, its spool-state version changes so stale executors/timers are closed and replaced under SPEC-004.C95/C96 reload semantics.
- **SPEC-004.C98:** A scheduler wake row contains at least a stable caller key, absolute wake instant, fully qualified handler symbol, persisted payload, status, attempt/fire/failure bookkeeping, and creation/update timestamps. Valid statuses cover pending, completed terminal history, cancelled, and failed; the exact table split is an implementation choice as long as pending and recent history/failure introspection stay data-first.
- **SPEC-004.C99:** Scheduling validates loudly before any durable write: the key must be a stable non-blank/non-nil value, `wake-at` must be an absolute instant shape the API accepts, the handler must be a fully qualified symbol resolvable in the weaver JVM/runtime classloader, and the payload encoding must be supported. Unsupported payload shapes and malformed timestamps are domain errors, never coerced defaults; a rejected schedule persists nothing.
- **SPEC-004.C100:** Startup and trusted config refresh re-arm pending scheduler rows only after selected activation files finish loading, so active spool handlers are resolvable before arming.
- **SPEC-004.C101:** Due detection is minimal: any pending wake with `wake-at <= now` is due and must be enqueued at least once (at-least-once delivery, not exactly-once — handlers must be idempotent). Malformed persisted rows fail loudly into failure introspection. Core does not implement cron, recurrence, retry/backoff, jitter, DST policy, missed-fire catch-up batching, or exactly-once semantics; a userland handler may schedule its own next wake.
- **SPEC-004.C102:** Scheduler handler invocation shares the existing serialized async dispatch worker by default, so clock-triggered handlers and post-commit event handlers observe one mutation lane rather than racing through independent worker pools. Queue-full is a transient delivery failure: it records an introspection failure but leaves or returns the durable wake to pending and re-arms it, so lane saturation cannot permanently drop a due wake before handler invocation. The durable delivery-attempt increment is generation-specific — it claims the exact wake generation selected (its key and wake instant) — so a wake cancelled or rescheduled in the race window between due-selection and the increment is never miscounted: a stale claim increments nothing, and a replacement generation's first real delivery still observes attempt 1. The increment is the first of two generation-sensitive transitions: it claims the delivered generation, and retirement (SPEC-004.C102b) releases that same generation, so a wake rescheduled in the delivery window is neither miscounted nor clobbered.
- **SPEC-004.C102a:** Due-detection and arming read the current instant from the runtime Clock
  (SPEC-004.C1a), not a private scheduler clock: the scheduler owns no separate time authority. It
  registers its due-check as a runtime clock-consumer pump, so manual Clock sleep and
  `millstrand.test.alpha/advance!` release due wakes synchronously without waiting on the real timer
  thread. Durable rows, at-least-once delivery (SPEC-004.C101/C102), and persisted `wake_at` millis
  are unchanged. Scheduler runtime state carries no clock slot.
- **SPEC-004.C102b:** Wake retirement is generation-aware. When a delivered wake is completed or failed, the scheduler retires exactly the delivered generation — the wake identified by its key *and* the delivered wake instant — and records its history entry from the delivered row (the row read before handler invocation), never from whatever pending row currently holds the key. A same-key replacement armed during delivery (the SPEC-004.C101-blessed self-reschedule) is a distinct generation: retirement leaves it untouched — no delete, no arming disturbance — and the post-fire re-arm (SPEC-004.C102) governs it. If the delivered generation has already vanished or been superseded by retirement time, retirement removes no pending row but still records the delivered fire in history, so at-least-once delivery stays observable. User-initiated cancel-by-key is not a delivery retirement and stays key-based: it cancels whatever generation currently holds the key.
- **SPEC-004.C103:** A handler is a fully qualified symbol resolved through the generation classloader and invoked with one context map containing the runtime, stable key, wake instant, attempt information, resolved handler symbol, and decoded payload. Return values are ignored. Handler-resolution failures and handler exceptions are captured in bounded recent failure/history data and never crash the weaver or the shared dispatch lane; idempotency remains the handler author's responsibility.
- **SPEC-004.C104:** The runtime exposes data-first scheduler introspection for pending wakes (ordered by wake-at ascending, so the earliest is the first pending wake), recent fires, recent cancellations, and recent failures. Recent history is bounded — the retention target is the latest 100 fires, cancellations, and failures per category, pruned during the write that records a new history entry. Introspection returns serializable maps and never exposes executor, timer, thread, or function objects.
- **SPEC-004.C105:** Scheduler tests must use deterministic clock/test seams. The runtime contract requires coverage for schema initialization, schedule/cancel/list persistence, startup re-arm, reload re-arm without duplicate fires, malformed schedule rejection, unresolvable handler failure capture, handler exception capture, and absence of scheduler rows from normal strand operations.

Design decisions: dedicated tables keep task queries, readiness, relation traversals, and graph burn/update semantics free of runtime coordination state while still giving the weaver enough durable state to re-arm after restart. The shared async lane is the default safety boundary — a separate scheduler worker would create a second mutation lane with different ordering/race behavior than post-commit events. There is no periodic safety tick in the contract: precise re-arm after scheduling, startup, and reload plus deterministic due-row tests are the arming mechanism, and a safety tick is added only if a concrete lost-arm window that precise re-arm cannot close is demonstrated.

## SPEC-004.P10e Weaver replacement and process custody

This section is shipped for Weaver replacement, admission, and Mill-owned process custody behavior.

The Mill router owns replacement of one Weaver generation while the Mill process remains alive. The Weaver remains the semantic owner of storage, registries, lifecycle effects, and domain policy. This section defines the Mill boundary needed for planned replacement; it does not turn restart into a durable workflow service.

Validation ownership is explicit. `millstrand.core.specs` owns `:millstrand.core.specs/restart-result`, `:millstrand.core.specs/mill-status-projection`, `:millstrand.core.specs/weaver-status-projection`, and `:millstrand.core.specs/admission-state`. The Mill wire adapter owns `:millstrand.core.mill-protocol/request` and `:millstrand.core.mill-protocol/response`, plus `validate-request!` and `validate-response!`. Mill consults the wire specs at decode and encode, the lifecycle result and status specs before command output, the Weaver status spec before socket status output, and the admission spec before every transition or invocation bind; malformed boundary data fails loudly.

- **SPEC-004.C113 (generation and restart state):** Every running Weaver publishes an opaque non-blank `generation_id` in `weaver.json`, `weaver.edn`, and socket status. A new process receives a new generation id, and a successful restart changes it exactly once. Mill owns one selected-workspace transition with states `probing`, `restarting`, `running`, and `failed`; its `:millstrand.core.specs/mill-status-projection` carries the state, selected workspace, generation id when one exists, transition id while a transition exists, and stage-specific diagnostics when a transition fails. The `:millstrand.core.specs/restart-result` validates each lifecycle result before Mill emits it. A restart from `running` or `failed` creates one transition. Restart callers joining `probing` or `restarting`, and start callers joining `restarting`, share that transition and receive its terminal generation or failure. A caller's readiness timeout starts when it joins and does not cancel the shared transition. Start during `running` or `probing` returns the admitted old generation. Start during `failed` returns the retained failed transition and admits no generation. Once `restarting` is visible, the old generation never returns to service. A failed probe returns to `running` with the old generation admitted; a failed cutover ends `failed` without admitting the old generation. Concurrent restart callers from `failed` join the one new probe, and a later successful restart admits exactly one replacement generation.
- **SPEC-004.C113a (persisted restart record):** Mill owns `restart.json` as a complete persisted restart record with `state`, `transition_id`, optional `generation_id`, optional `previous_generation_id`, optional non-blank `previous_weaver_id`, writer-owned `updated_at`, optional successful `probe`, optional `failure`, and `old_generation_stopped`; the record validator rejects unknown, malformed, missing, and state-contradictory fields before every mutation/write and again after decode on read, and refusal is loud with no fallback or partial record use. The peer boundary uses the same closed shape when it reads a present record.
- **SPEC-004.C113b (stale artifact reclamation):** Startup may reclaim runtime artifacts only after proving complete world identity, a dead recorded owner, and an inactive socket; live, malformed, mismatched, or unknown owners are never reclaimed, and a held successor claim blocks deletion.
- **SPEC-004.C114 (fresh-generation probe):** Before closing old-generation admission, Mill constructs a disposable probe workspace from the selected workspace's effective configuration while retaining the original repository and configuration roots as source-resolution authorities. The probe has fresh storage, runtime state, and JVM classloader. Its public boundary requires an admitted old-generation baseline containing the complete C26 projection; missing, malformed, unavailable, or empty-fallback evidence fails before startup. It materializes roots, resolves dependencies, runs the existing effect-free refresh coordinator, collects the complete layered module graph and selected authoring declarations, stages candidate registries, runs candidate validators, resolves lifecycle callables, and writes a lifecycle plan. Candidate and baseline projections use C26's stable redacted representation; their semantic diff reports exact added, removed, and changed kinds. Probe mode publishes no candidate registry or canonical Weaver metadata, opens no lifecycle resource, invokes no seed or reconcile effect, rearms no scheduler row, delivers no event, and launches no custodied process. Diagnostics are structured and written incrementally with root/module outcomes, candidate projection and diff, unexecuted lifecycle plan, completed/skipped stages, failure context, and logs. A completed lifecycle-plan record carries the complete plan; an unavailable plan is explicitly skipped with `available? false`, its reason, and an empty plan. Diagnostic sink failures are loud; while reporting an existing probe failure they are attached as suppressed context rather than replacing it. A failed probe is stopped and retained with its path; a successful probe is stopped and removed before cutover. After a successful probe, Mill atomically closes old-generation admission and records `restarting` before stopping the old process. Probe mode does not sandbox trusted top-level evaluation or make a passing probe a startup guarantee. Replacement startup remains authoritative and reports its stage, logs, and exit evidence on failure.
- **SPEC-004.C115 (admission and one-send boundary):** Mill owns one per-workspace admission gate shared by lifecycle transitions and forwarded invocation requests. The gate state conforms to `:millstrand.core.specs/admission-state`; every transition and bind consults that spec before changing or using the state. Mill's internal envelopes conform to `:millstrand.core.mill-protocol/request` and `:millstrand.core.mill-protocol/response`; the wire adapter validates them at decode and encode. Before its first Weaver socket write, an invocation atomically binds to the current admitted generation or waits on the shared restart transition. While `probing`, the old generation remains admitted. When Mill closes admission and records `restarting`, no later invocation binds to the old generation. The invocation captures its transition and admission epoch before releasing the workspace admission lock; a later socket failure may be relabelled only when the cutover is causally the same transition and epoch, and the selected old weaver and generation identities both match. A waiting invocation is not placed in a persisted queue: it binds and writes once when the replacement is ready, or returns the shared failure, existing deadline result, or cancellation without writing. The first socket write is the send boundary. A request written once is never replayed, even when its response is lost during cutover; an interrupted accepted request returns `weaver/restarted` with sent-once, response-ambiguous evidence, or the existing transport result. Direct Weaver-socket and nREPL clients are outside this gate and reconnect after an ordinary disconnect.
- **SPEC-004.C115a (relay delivery evidence):** Mill tracks possible request delivery separately from response delivery. A response is successful only after at least one complete newline-delimited frame; truncated or garbage partial data followed by EOF emits a transport error, and the request is never replayed.
- **SPEC-004.C116 (Weaver-to-Mill custody protocol):** The trusted process API reaches Mill through a local Weaver-to-Mill control channel, not through `strand` or a public JSON socket operation. Each control request is one JSON object with exactly `protocol_version`, `request_id`, `weaver_id`, `operation`, and `arguments`; `operation` is one of `process.launch`, `process.get`, `process.list-owned`, `process.cancel`, or `process.acknowledge`. `arguments` carries the boundary data from SPEC-003.C71-C74, with JSON field names `owner`, `key`, `launch_spec`, or `handle` as applicable; `launch_spec.argv` is a non-empty string array passed directly to the operating system without shell parsing. The response uses the existing versioned request identity and success/error envelope, returning one process record or one data-first acknowledgement result. The named `:millstrand.core.weaver.process-protocol/control-request` and `:millstrand.core.weaver.process-protocol/control-response` specs, plus `validate-request!` and `validate-response!`, own this wire boundary. The channel binds the selected workspace; Mill verifies the calling generation and rejects stale, malformed, mismatched, or unknown identities loudly. These frames are internal control glue and add no public CLI command or socket operation.
- **SPEC-004.C117 (custody record shape):** Mill custody records carry `handle` (opaque non-blank string), `owner` (stable owner keyword encoded as a non-blank string), `key` (non-blank string), `phase` (`starting`, `running`, or `terminal`), and `output` with non-blank `stdout_ref` and `stderr_ref` values. A terminal record carries exactly one result: `exit` with integer `code` and nullable string `signal`, `cancellation` with a non-blank string `reason`, or `launch_failure` with exactly `message` containing a non-blank string; non-terminal records carry none of these result fields. The public Clojure projection maps `launch_failure` to `:launch-failure {:message string}`. `launch` reserves `[owner,key]` atomically with the complete launch specification. Repeating the same owner, key, and specification returns the existing record in its current phase; a different specification for an existing reservation is a loud conflict. A handle is the addressable identity; a PID is diagnostic only.
- **SPEC-004.C118 (Mill-lifetime custody):** Mill stores custody reservations, process identity, process-tree membership, stdout/stderr references, and terminal facts in the selected workspace's Mill-owned state. Mill alone resolves `starting` to `running` or a terminal launch failure, represented as `launch_failure: {message: <non-blank string>}` on the wire and `:launch-failure {:message <non-blank string>}` in the public record; a spool never reconstructs a partial launch and inspects the record again during reconciliation. Mill starts the registered process tree, uses PID-reuse-safe identity checks, retains output and completion facts while the store remains available, and cancels the whole tree for `process.cancel`. A custodied child continues while its Weaver is replaced, including while the old Weaver is stopping and the replacement is starting. Clean Mill shutdown terminates owned process trees and records terminal cancellation when its store remains available. Abrupt Mill death, orphan adoption, and transfer to a new Mill process are outside the contract; no cross-Mill survival is promised.
- **SPEC-004.C119 (retention and acknowledgement):** A terminal fact remains enumerable through `process.get` and `process.list-owned` until its owning spool acknowledges the handle. Acknowledgement accepts only a terminal record with the matching owner, removes it from owner enumeration, and permits output cleanup while retaining the `[owner,key]` tombstone that prevents relaunch during the selected Mill lifetime. Mill may observe a terminal fact more than once before acknowledgement. Cancellation is idempotent and never erases a terminal record. Missing handles, owner mismatches, non-terminal acknowledgement, contradictory records, and malformed persisted facts fail loudly.
- **SPEC-004.C120 (owner reconciliation):** Replacement activation runs each migrated owner's existing module-owned `defreconcile!` effect after its module source and required durable state are available. The effect compares the owner's durable active records with `process.list-owned`, preserves matching `starting` or `running` claims and schedules a later check, and applies matching terminal results idempotently before acknowledging them. Missing domain records, missing or mismatched handles, and owner or attempt conflicts are recorded as owner-local reconciliation failures requiring intervention; the runtime does not guess repair or block unrelated modules. Failure to reach custody or enumerate an owner means continuity cannot be assessed and fails replacement startup visibly.
- **SPEC-004.C121 (interruption outcomes):** Restart interrupts in-JVM work at the existing ownership boundary. Legacy `agent-run` and `harness-core`/`agent-cli` paths converge on custody-backed agent delegation before release, and Millhouse shell execution uses custody and owner reconciliation; a Millhouse code-executor callback records interruption and clears its running claim so its spool policy can mark the gate retryable. A scheduler handler already running is interrupted; its existing durable at-least-once row re-arms and may run again. An event-lane or Chime delivery in flight is interrupted and not replayed; a producer that requires delivery owns a durable outbox and republish policy. A peer call either completes before shutdown or returns `weaver/restarted` without automatic retry. The peer boundary validates a present `restart.json` record strictly, then requires both `previous_weaver_id` and `previous_generation_id` to match the selected old peer before classifying a sent request as a planned interruption. That result carries sent-once and response-ambiguous evidence; callers may reconnect and reissue only an explicitly safe read. A connected REPL or editor nREPL session observes a socket close and reconnects to the replacement. A Mill-routed stream or await accepted by the old generation ends with `weaver/restarted`; a not-yet-sent request follows C115, and any safe rearm belongs to the owning client or spool. Ralph waits for readiness and may explicitly reissue a safe read, while mutations are never reissued automatically. Interactive backends retain their separate lifecycle contract.
- **SPEC-004.C122 (restart scope):** The restart contract covers the ordinary planned replacement while one Mill remains alive. It does not provide a persistent request journal, transparent accepted-request replay, speculative rollback, JVM computation transfer, universal subprocess migration, exactly-once external effects, or recovery after Mill exit. Spools own idempotency, checkpoints, durable outboxes, ambiguity handling, and the mapping from custody facts to domain state. Missing or conflicting evidence is visible and fails at its owning boundary rather than receiving a guessed default.
- **SPEC-004.C123 (replacement coverage):** The repository's replacement tests must prove that a failed probe leaves the old generation serving with retained diagnostics, a valid probe permits one generation cutover, concurrent callers converge, waiting and admitted requests observe the C115 send boundary, startup failure is visible, caller timeout does not cancel shared restart, and custodied native work survives with terminal reconciliation. Focused contracts cover all custody phases, idempotent launch, agent delegation, Millhouse shell-gate completion, cancellation and acknowledgement, owner-local reconciliation conflicts, peer-call interruption, connected-REPL disconnect, scheduler rearm, accepted await interruption, safe read reissue, and clean Mill shutdown cancellation. Other interruption timing has an explicit owning contract rather than an exhaustive crash matrix.

Traceability for the frozen proposal is direct: `PROP-Wrc-001.G1` maps to C113-C114, G2 to C115, G3 to C116-C119, G4 to C120 and C122, and G5 to C121. `S1` maps to C113-C114, S2-S3 to C115, S4 to C116-C119, S5-S5a to C119-C120, S6 to C118 and C122, S7-S8 to C121, and S9 to C123. `P3` and `P3a` are bounded by C113, C115, and C122; `NG1-NG5` are explicit in C115 and C122; and `P8` is the custody ownership rationale in C116 and C118. The brief's acceptance obligation to cover restart, client admission, process custody, owner reconciliation, and interruption across Millstrand, Millhouse, agent, and Codethread surfaces is addressed by C113-C123, with domain-specific state changes left to the owning spool.

## SPEC-004.P11 Removed compatibility

The weaver runtime and clients do not support compatibility lookup of old default `atom` workspaces, `tasks.sqlite`, `daemon.*` metadata, or `todo.*` / `atom.*` namespaces.
